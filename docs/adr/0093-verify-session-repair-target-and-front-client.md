# 0093. 세션 복구가 목표 소스로 끝났는지 확인하고 앞 앱의 세션만 확인한다

- 상태: Accepted (구현·회귀 테스트, 카카오톡 재발 여부는 추가 관찰)
- 날짜: 2026-10-21
- 관련: [0062](0062-repair-input-method-session-with-previous-source-shortcut.md), [0070](0070-acknowledge-only-open-sessions-and-retry-repair.md), [0082](0082-key-acknowledgement-system-abc-and-suspect-log.md), [0091](0091-restore-a-switch-macos-undoes.md)

## 맥락

카카오톡 대화 입력창에서 한글 입력기가 선택돼 있는데 영문만 입력된다는 보고가 있었다. 사용자는 확인 중 정상으로 돌아왔다고 했다.

문제 발생 당시 실행 앱은 0.3.7(149)이었다(09:34:56 시작 로그). 아래 세션 복구 문제는 0.3.6의 전환 되돌림 보완(0091)이 들어간 뒤에도 발생했다.

09:36:46에 카카오톡으로 돌아오면서 한글을 선택했고, macOS가 영문으로 덮어써 한글을 다시 선택했다. 이어 세션 복구가 이전 소스 단축키를 두 번 보냈지만 09:36:47.318의 최종 소스는 ABC였다(`unrepaired`). 그 뒤 카카오톡의 새 세션은 영문으로 활성화돼 실제 키도 영문 모드로 받았다. 두 번 전환하면 원래 목표로 돌아온다는 가정이 깨졌다.

09:37:09에는 표시가 한글로 바뀌었지만 카카오톡 세션의 마지막 모드 콜백은 영문이었다. 키를 받을 때 모드를 맞추는 코드가 있으므로 이 기록만으로 실제 출력까지 단정하지 않는다. 09:38:03에는 카카오톡 입력기에 한글 모드로 키가 도착했다. 입력 내용은 기록하지 않는다.

별도로, 선택 알림의 확인과 달리 활성화·모드 콜백의 확인은 앞 앱인지 검사하지 않았다. 뒤 앱에 남아 있는 활성 세션의 지연 응답이 앞 앱의 복구를 취소할 수 있어 같은 조건으로 제한한다. 이번 발생의 직접 원인인지는 로그만으로 확정하지 않는다.

## 결정

- 두 단축키 처리 후 실제 소스가 목표와 같은지 확인한다. 다르면 같은 앱이 앞에 있고 복구가 가능한 동안 목표를 한 번만 다시 선택하고 확인 시간을 새로 둔다.
- 재선택 전의 확인 응답은 지운다. 새 선택의 응답과 최종 소스가 모두 맞아야 `repaired`다. 재선택 실패·재덮어쓰기·응답 없음은 `unrepaired`이고 반복하지 않는다.
- 두 번째 단축키 전과 최종 확인 때 앞 앱을 다시 확인한다. 앱이 바뀌면 새 앱에 키나 재선택을 보내지 않는다. 다른 문맥의 응답도 기다리던 선택을 확인할 수 없다.
- 활성화·모드 콜백의 확인에도 앞 앱 조건을 적용한다. 입력 내용과 창 제목은 읽거나 기록하지 않는다.

## 검증

- 세션 복구 회귀 테스트: ABC로 끝난 복구, 재선택 뒤 새 확인 필요, 재덮어쓰기의 제한, 선택 실패, 두 키 사이·최종 확인 전 앱 변경, 다른 문맥의 확인 응답.
- 세션 확인 회귀 테스트: 뒤 앱의 활성 모드 콜백은 두 모드 모두 확인하지 않는다.
- 실제 카카오톡 대화 입력창의 재발 여부는 사용자 확인과 후속 로그로 관찰한다. 자동 검사에서는 개인 대화창에 글자를 넣지 않는다.
- 초기 로컬 0.3.5 기반 `scripts/verify.sh` 통과: Swift 1,222개, 스크립트 142개, 사이트 34개, 정적 검사·서명 번들·입력기 자체 검사(`.artifacts/verify/20261021-094056/`). 이후 복구 회귀 사례를 한글·영문 양쪽으로 확장해 29개 테스트를 다시 통과했다.
- 설치본과 입력기를 업데이트했고, 설치된 실행 파일이 검증 번들과 같은지 확인했다. 입력기 업데이트·반복 설치 검사도 통과했다.
- 실제 IMK 임시 클라이언트 검사 통과: 기본 입력·복합 받침·삭제·경계 키·반복 한/영 전환과 첫 키(`.artifacts/input-method-e2e/20261021-094610/`). 첫 실행(`094241/`)은 복합 받침의 조합 표시 검사에서 실패했고, 같은 코드의 재실행은 모두 통과했다. 최초 실패의 원인은 확정하지 못했다.
- TextEdit의 복구 단축키 검사는 문서 포커스 준비 중 `AXFocusedWindow` 접근 오류로 중단됐다(`.artifacts/input-method-textedit/20261021-094550/`). 실제 TextEdit 복구 경로의 통과로 세지 않는다.
- 최종 검증은 원격 main `6e43424`(0.3.7) 위에 패치를 보존해 진행했다. 원격 4커밋은 이번 코드·테스트 6개 파일을 바꾸지 않았고, 기존 패치와 동일함을 대조했다(문서 번호만 0093으로 변경). 0091의 전환 감지는 세션 복구 중 알림을 건너뛰고 복구 완료 시 기준선을 초기화하므로 목표 재선택과 겹쳐 동작하지 않는다.
- 최종 `scripts/verify.sh` 통과: Swift 1,237개, 스크립트 142개, 사이트 34개, 정적 검사·서명 번들·입력기 자체 검사(`.artifacts/verify/20261021-095248/`). 최종 실제 IMK 검사도 첫 실행에 모두 통과했다(`.artifacts/input-method-e2e/20261021-095422/`).
- 최종 설치 앱·내장 입력기·설치 입력기는 모두 0.3.7(149)이다. 설치된 두 실행 파일이 검증한 패치 빌드와 SHA-256으로 일치하고, 서명 검증 및 실행 로그의 `needsUpdate=false ready=true`도 확인했다.
