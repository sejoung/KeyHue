# 0059. 외부 입력 소스 변경 알림에서 검증된 조합만 확정한다

상태: Accepted (TextEdit 외부 전환의 조합 보존 검증, 진입·콜드 스타트는 별도 과제)

날짜: 2026-10-03

## 배경

[ADR 0058](0058-external-mode-callbacks-and-native-editor-acceptance.md)의 TextEdit 검사는 입력 메뉴에서 전환하면 통과했지만 별도 프로세스가 TIS로 영문을 선택하면 보이던 `안`이 다음 `a`에 덮였다. 전환 뒤에도 기존 조합을 끝내는 IMK callback이 도착하지 않은 실행이 있었다. 선택된 source ID만으로 문서의 조합 종료를 판단할 수 없다.

[Apple IMKInputController 문서](https://developer.apple.com/documentation/inputmethodkit/imkinputcontroller)의 세션별 컨트롤러·연결된 클라이언트 계약과 SDK의 `kTISNotifySelectedKeyboardInputSourceChanged` 알림을 사용한다. [Squirrel의 macOS 26 외부 TIS 전환 보고](https://github.com/rime/squirrel/issues/1140)와 [후속 수정](https://github.com/rime/squirrel/pull/1142)도 유사한 callback 누락을 다룬다. 이를 모든 OS·클라이언트에서 같은 원인이 발생한다는 증거로 사용하지 않는다.

## 결정

- 활성 컨트롤러가 선택 소스의 distributed notification을 `deliverImmediately`로 받는다. 메인 스레드에서 자기 모드와 다른 소스가 선택됐고 미확정 글자가 있을 때만 확인한다. 알림은 엔진의 다음 모드를 선택하거나 입력 소스를 다시 요청하지 않는다.
- 연결된 클라이언트의 비어 있지 않은 bundle ID가 현재 전면 앱과 일치해야 한다. 유효한 marked range의 UTF-16 길이가 자기 미확정 문자열과 같고, 기존 caret 해석으로 삽입점이 조합 끝에 있어야 한다. 그 범위만 읽어 문자열도 정확히 비교한다. 범위를 제공하지 않는 앱에는 이 보완 편집을 적용하지 않는다.
- RPC 조회 뒤 클라이언트 객체·활성 상태·전면 앱·선택 소스·marked range·selected range·미확정 문자열·context 세대가 그대로인지 다시 확인한다. 키·활성화·확정·취소·비활성화·모드 callback은 세대를 바꿔 재진입 중 낡아진 확인을 버린다.
- 검증된 marked range를 명시한 `insertText`로 남은 조합을 한 번 확정하고 고침 context를 폐기한다. 현재 선택 위치를 뜻하는 sentinel range로 다른 위치에 쓰지 않는다. 코어 버퍼가 비워지므로 늦은 알림·비활성화가 같은 글자를 다시 삽입하지 않는다. 정상 callback이 조회 중 먼저 처리되면 세대 검사에서 알림의 편집을 생략한다.
- 서버 로그에는 source ID·범위 길이·세션과 처리 단계만 남기고 입력 글자·키 코드는 남기지 않는다. `composition finalized`는 코어 확정과 편집 요청을 뜻한다. 반환값 없는 IMK 편집 API의 문서 반영 성공은 실제 클라이언트 결과로 별도 확인한다.
- TextEdit 검사는 같은 창에서 `안`을 조합한 뒤 worker로 ABC 또는 KeyHue 영문을 선택하고 `a + Space`를 보내 `안a `를 확인한다. 창 이동 callback 없이 재현한다. 창 왕복 사례도 유지한다. 초기 `안` 조합부터 실패하면 외부 전환 검사는 생략하고, 보존 실패 뒤에는 잔여 조합이 다음 사례를 오염시키지 않도록 종료한다.
- 기본 준비는 실제 입력 메뉴로 하여 이미 조합 중인 context에서 **떠나는** 경로를 분리한다. `KEYHUE_TEST_TEXTEDIT_PREPARE_MODE=worker`로 원래의 programmatic 진입도 별도로 재현할 수 있다. 키 직전 source ID 조회는 실제 context 준비 완료와 동일하지 않다. 일반 앱의 자동 고침은 여전히 허용하지 않는다.

## 검증과 한계

macOS 26.6.2 (25G83), arm64, TextEdit 1.20, Swift 6.4 / macOS 27 SDK에서 검사했다. 비교본은 commit `9d6ddef`의 입력기 코드이며 임시 빌드 메타데이터만 최종 설치본과 같은 0.2.5·빌드 74로 맞췄다. 동일한 현재 runner·메뉴 준비·worker 이탈·임시 일반 텍스트 문서로 비교했다.

| 경로 | 이전 코드 | 수정 코드 |
|---|---|---|
| 같은 창, worker ABC 전환 | `안` 준비 통과 후 `a `로 유실 (`181413`) | `안a ` 보존·창 왕복 통과 (`182358`) |
| 같은 창, worker KeyHue 영문 전환 | `안` 준비 통과 후 `a `로 유실 (`181843`) | `안a ` 보존·창 왕복 통과 (`182711`) |

위 결과는 `.artifacts/input-method-textedit/20261003-<시각>/`에 있다. `182711`에서는 다음 키와 비활성화 전에 알림 경로의 확정 요청을 확인했다. `182358`의 조회 도중에는 정상 비활성화가 재진입해 알림 경로의 추가 편집을 생략했으며 결과는 보존됐다. 모든 성공이 보완 편집만 거친 것으로 해석하지 않는다. worker 준비까지 사용한 `183113`도 통과했고 두 조합의 알림 확정 로그가 있지만, 앞선 `174046`·`174123`은 초기 조합이 `dks`로 남아 전환 검사를 시작하지 못했다. 서버에 키가 들어오지 않는 진입 문제의 해결 증거로 마지막 통과를 사용하지 않는다.

최종 코드의 전체 자동 검증 `.artifacts/verify/20261003-180551/` 통과: Swift 849개(Core 524·App 242·실험 Core 83), 스크립트 115개, 사이트 34개, lint, 앱/서비스 빌드·서명·self-check. 코어 회귀 검사는 다른 소스의 검증된 조합만 한 번 확정하고 동일/누락 소스와 불일치 문자열은 유지하는지 검사한다. `.artifacts/input-method-e2e/20261003-182034/`에서 전용 Cocoa 기본·고침·되돌리기·다음 키 경합·필드 이동·외부 선택 취소와 실제 업데이트·반복 설치도 통과했다. 최종 TextEdit 입력 메뉴 전체 `183437`에서 일반 텍스트·RTF 기본 11개씩과 같은 창 조합·창 왕복도 통과했다. 환경 복원 근거는 [호환성 기록](../INPUT_METHOD_COMPATIBILITY.md)에 남긴다.

이 변경은 확인된 외부 전환에서 남은 조합 보존을 해결한다. 알림 전 다음 키·빠른 왕복·알림 누락, 진입 첫 키·콜드 스타트, 유틸리티 자동 연동·전환 단축키, 다른 앱·보안 필드와 범위를 제공하지 않는 클라이언트는 별도 검사 대상이다. 동기 RPC의 지연·실패와 제품 성능 보장도 완료되지 않았다. 판정기·설정·일반 앱 고침 옵션은 다음 단계다.
