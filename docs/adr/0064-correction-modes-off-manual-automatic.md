# 0064. 입력기 단어 고침은 끄기·수동·자동 세 가지로 고르고, 기본은 수동이다

상태: Accepted ([0068](0068-fix-words-with-a-shortcut.md)에서 수동을 한/영 전환 대신 단축키 요청으로 바꿨다. 정책·판정기·설정 UI·자동 연결 구현, 테스트 앱과 TextEdit에서 수동·자동 실제 검사 통과. 고침 허용 앱은 TextEdit, 다른 앱은 앱별 검사 후 추가. 교체 확인 앱 허용 목록은 [0065](0065-correct-all-apps-with-feedback.md)로 대체)
날짜: 2026-10-04

관련: [0040](0040-mistype-language-detection-phase0.md), [0041](0041-wrong-language-warning.md), [0045](0045-experimental-input-method-component.md), [0056](0056-isolated-correction-and-undo-probe.md), [0057](0057-automatic-correction-observation-and-input-priority.md), [0058](0058-external-mode-callbacks-and-native-editor-acceptance.md)

## 배경

[ADR 0045](0045-experimental-input-method-component.md)는 입력기의 자동 고침을 별도 옵션으로 두고 기본 OFF로 정했다. [ADR 0056](0056-isolated-correction-and-undo-probe.md)~[0058](0058-external-mode-callbacks-and-native-editor-acceptance.md)은 전용 테스트 앱과 `dkssud` 한 단어로 다음 편집 경로를 검증했다.
- Space에서 교체하고 한글 모드로 바꾼다.
- 바로 Backspace를 누르면 되돌린다.

판정기([ADR 0040](0040-mistype-language-detection-phase0.md))와 실제 앱에는 아직 연결하지 않았다.

제품 기능으로 만들 때 사용자가 고르는 방식이 필요하다.
- **자동만 있는 경우:** 판정이 틀리면 사용자가 쓴 영어 단어가 바뀐다. 말뭉치 오탐률은 낮았지만 실제 입력에는 아직 검증되지 않았다. 코드 식별자, 약어, 섞어 쓰기, 명령어 같은 입력이 그렇다.
- **끄기만 있는 경우:** 입력기를 설치한 이유, 즉 잘못 친 단어를 다시 치지 않으려는 목적이 사라진다.

KeyHue 입력기를 설치하고 선택한 것은 고침을 쓰겠다는 의사로 본다. 다만 자동 교체까지 허락했다고 보지는 않는다.

사용자는 잘못 친 것을 알아채면 대부분 한/영 전환 키를 누른다. 그 동작을 "고쳐 달라"는 신호로 쓰면 새 키나 확인 절차가 필요 없다.

## 결정

### 세 가지 모드

| 모드 | 동작 |
|---|---|
| **끄기** | 고치지 않는다. 기본 입력만 한다. |
| **수동** (기본값) | 판정기가 오타로 본 단어 **직후에 사용자가 한글 모드로 전환하면** 그 단어를 한글로 고친다. |
| **자동** | 판정기가 오타로 본 단어를 Space 같은 단어 경계에서 바로 고치고 한글 모드로 바꾼다(ADR 0056의 계약). |

- 기본값은 **수동**이다. 판정이 틀려도 사용자가 전환하지 않으면 아무 일도 일어나지 않는다. 실제 사용에서 오탐률 근거가 쌓이면 자동을 권하거나 기본값을 다시 판단한다.
- 첫 범위는 **영문 → 한글**이다. 한글 모드에서 친 영어 단어를 고치는 반대 방향은 같은 모드 구조로 나중에 더한다. ([ADR 0067](0067-bidirectional-correction-and-terminals.md)에서 수동의 반대 방향과 터미널을 더했다.)
- 모드 이름과 설명은 KeyHue 앱의 표시 언어(영어·한국어·일본어) 모두로 번역한다. 입력 언어가 아니라 설정 화면 문구의 번역이다. 입력기는 한글·영문 두 모드만 있다. 설정은 KeyHue UI가 소유한다. 입력기는 유틸리티가 실행 중이 아니어도 마지막으로 저장된 모드를 따른다(ADR 0045).

### 수동 모드: 전환 직후 고침

- **고칠 단어:** 영문 모드에서 방금 친 단어다. 두 경우를 포함한다.
  - 단어 경계(Space·Return·Tab)까지 친 단어.
  - 아직 경계 없이 치는 중인 단어.
- **신호:** 입력기 세션이 영문 → 한글 모드 변경을 받는 것이다. 메뉴, `⌘Space` 등 이전 입력 소스 단축키, Caps Lock, KeyHue 유틸리티의 전환을 구분하지 않는다. 입력기가 어느 경로였는지 알 수 없고 알 필요도 없다.
- **고치는 조건:** 단어와 전환 사이에 다른 입력이 없어야 한다. 다음 중 하나라도 있으면 후보를 버린다.
  - 다른 키, 클릭, 커서·선택 이동.
  - 포커스·앱·필드 변경, 외부 편집.
- **판정기 게이트:** 판정기가 한글 후보로 본 단어만 고친다. 예를 들어 `hello `를 치고 다음 단어를 한글로 치려고 전환한 경우에는 바꾸지 않는다. 사용자가 이미 의사를 보였으므로 자동보다 완화된 임계값을 쓸 수 있다. 두 임계값은 각각 실제 사례로 정한다.
- **모드:** 고친 뒤 모드는 사용자가 고른 한글 그대로다. 입력기가 따로 모드를 바꾸지 않는다.
- **되돌리기:** 바로 Backspace를 누르면 원문으로 되돌린다. 모드는 그대로 둔다. 전환은 사용자의 선택이었고, 다음 단어를 한글로 치려 했을 수 있기 때문이다. 자동 모드의 되돌리기는 이전처럼 영문 모드도 되돌린다.
- **ADR 0058과의 관계:** 0058은 외부 모드 요청이 대기 중인 고침을 취소한다고 정했다. 이는 자동 모드에서 유지한다. 수동 모드에서는 그 모드 변경이 고침의 신호다.

### 모든 모드에 공통

- **고치지 않는 곳:**
  - 보안 입력 칸.
  - 사용자 제외 목록의 앱. 터미널과 코드 편집기는 처음부터 목록에 넣고, 사용자가 앱을 추가하거나 뺄 수 있다.
  - 범위 교체·원문 확인을 할 수 없는 앱. 자동 모드여도 고치지 않는다.
- **편집 계약:** 교체 범위, 원문·세션 확인, 실패 시 원문 복구, UTF-16 범위는 ADR 0056·0057의 계약을 그대로 따른다. 원문 유실, 공백 중복, 모드 불일치는 배포 차단 결함이다.
- **개인정보:** 원문·후보·결과는 입력기 메모리에만 둔다. 저장, 전송, 로그 기록을 하지 않는다. 로그에는 모드와 결과 분류만 남긴다.
- **유틸리티 경고와의 관계:** 입력기 선택 중에는 유틸리티의 한/영 경고 추적을 계속 중단한다(INPUT_METHOD_DESIGN §6). 수동 모드에서 "한/영 키를 누르면 고칩니다" 같은 안내를 보일지는 별도로 정한다. 단어 내용을 입력기 밖으로 보내지 않는 방식이어야 한다.

## 진행 순서

1. **수동 신호 실험:** 전용 테스트 앱에서 다음을 확인한다.
   - 영문 단어 직후 메뉴, `⌘Space`, Caps Lock, 유틸리티 전환 각각에 대해 입력기가 모드 변경을 받는 시점에 직전 단어를 아직 확인·교체할 수 있는지.
   - 경계가 이미 확정된 단어와 치는 중인 단어 모두.
   - 모드 변경 callback과 source-change 알림의 순서.

   결과에 따라 이 ADR의 수동 계약을 확정하거나 고친다.
2. **Core 정책과 순수 테스트:** 모드별 고침 여부, 수동 신호의 유효 조건과 무효화, 되돌리기 시 모드 처리, 제외 조건을 테스트로 먼저 고정한다.
3. **판정기 연결:** 판정기를 `dkssud` 고정 사례 대신 연결한다. 수동·자동 임계값을 실제 사례와 말뭉치로 각각 잰다.
4. **설정 UI:** 세 모드 선택과 앱 제외 목록을 만들고 설정 문구를 앱 표시 언어(영어·한국어·일본어)로 번역한다.
5. **실제 앱 검증:** 앱별 교체 능력을 판별하고 호환성 표(TextEdit부터)를 채운다.

## 수동 신호 실험 (2026-10-04)

전용 테스트 앱 `io.github.sejoung.keyhue.testclient.manual-probe`와 `dkssud` 고정 사례로 실험했다. 입력기 쪽은 실험용 `IMKManualSignalProbe`가 담당했고 판정기와 설정은 쓰지 않았다. 이후 정책·판정기를 쓰는 `IMKManualCorrection`으로 바꿨다(아래 판정기 연결). 테스트 앱이 보낼 수 없는 전환(HID 단축키, 입력 메뉴, 다른 프로세스)은 셸 runner가 요청을 받아 실행한다(`KEYHUE_TEST_MANUAL_PROBE=1`).

입력기 동작:
- 한글 모드 신호를 처음 받으면 10ms 뒤부터 다음을 확인한다. 같은 클라이언트인지, 조합 중인 글자가 없는지, 커서가 단어 끝인지, 원문이 그대로인지. 확인되면 한 번 교체하고, 다음 관찰에서 결과를 확인한다.
- 같은 전환의 두 번째 신호는 기록만 한다.

| 전환 경로 | Space까지 친 단어 (`dkssud ` → `안녕 `) | 치는 중인 단어 (`dkssud` → `안녕`) | 먼저 온 신호 |
|---|---|---|---|
| 테스트 앱 안의 TIS 선택 | 고침, 되돌리기 통과 | 고침, 되돌리기 통과 | 모드 callback 또는 선택 변경 알림 |
| 다른 프로세스(KeyHue worker, 유틸리티와 같은 API) | 고침 | 고침 | 선택 변경 알림만 |
| 설정된 이전 입력 소스 단축키(`⌘Space`, HID) | 고침 | 고침 | 모드 callback |
| 입력 메뉴 | 고침 | 고침 | 모드 callback 또는 선택 변경 알림 |

대조군은 모두 바뀌지 않았다.
- `hello `
- `dkssud ` 뒤 새 단어 `r`
- `dkssud ` 뒤 ←·→ 커서 이동

세 번 반복한 결과가 같았다(`.artifacts/input-method-e2e/20261004-104541/`, `104613/`, `104637/`). 신호부터 교체 요청까지 10~15ms였다.

확인한 사실:
- 네 경로 모두 전환 직후 직전 단어를 확인하고 교체할 수 있었다. 치는 중인 단어의 마지막 글자 조합은 신호를 처리하는 사이에 확정됐다.
- 다른 프로세스의 선택은 모드 callback 없이 선택 변경 알림으로만 왔다. 다른 경로는 두 신호가 모두 오며 순서는 일정하지 않다. 따라서 두 신호를 모두 받고, 한 번의 전환으로 묶어야 한다.
- 바로 누른 Backspace는 교체 결과를 관찰하기 전에 도착했다. 첫 실행(`104252/`)에서는 되돌리기 대상이 아직 등록되지 않아 일반 삭제가 됐다. 그래서 요청만 한 교체도 Backspace 시점에 화면 결과를 직접 확인하고 되돌리도록 고쳤다. 이후 세 번 모두 원문이 복원됐고 모드는 한글로 유지됐다.
- Caps Lock 전환은 HID로 재현할 수 없어 실험하지 않았다. 실제 키로 확인해야 한다.

KeyHue 유틸리티의 자동 전환도 같은 신호로 보인다. 다만 자동 전환을 일으키는 사건(앱·필드 변경, ESC 등)은 그 전에 후보를 버린다. 유틸리티 전환이 고침을 일으키는 경우가 남는지는 제품 정책 테스트에서 따로 확인한다.

## Core 정책 (2026-10-04)

`CorrectionPolicy`(입력기 Core)는 이벤트를 받아 고칠지, 되돌릴지만 결정한다. 편집 요청과 클라이언트 원문 확인은 IMK 어댑터가 한다. 판정기는 `CorrectionJudging`으로 주입하며 모드(`manual`·`automatic`)별 임계값을 받는다. `CorrectionPolicyTests`가 다음을 고정한다.

- **수동:**
  - Space까지 친 단어와 치는 중인 단어를 한글 전환 신호에서 고친다. Space만으로는 고치지 않는다. 모드 요청은 보내지 않는다.
  - 단어와 신호 사이에 다음이 끼면 고치지 않는다: 다른 키, Return·Tab, 두 번째 Space, 클릭, 커서 이동, 문맥 변경, 외부 편집.
  - 영문·외부 소스로의 전환은 후보를 버린다.
  - 같은 전환의 중복 신호는 무시하고 되돌리기를 유지한다.
  - 되돌리기는 글자만 원래대로 한다.
  - 마지막 단어만 본다.
- **자동:**
  - Space에서 고치고 한글 모드를 요청한다. 전환 신호는 기다리지 않는다.
  - 되돌리기는 Space 없는 원문과 영문 모드로 돌린다. 같은 단어의 다음 Space는 다시 고치지 않는다.
  - 외부 모드 신호는 되돌리기를 취소한다(ADR 0058).
- **공통:**
  - 끄기, 보안 입력, 제외 앱, 교체를 확인할 수 없는 앱에서는 판정기를 부르지도 않는다.
  - 되돌리기는 바로 다음 Backspace 한 번뿐이다.
  - 다음 경우는 후보가 아니다: 한글 모드 글자, 단어 시작이 아닌 곳에서 시작한 글자, 커서가 건너뛴 글자, 숫자·기호, 40타 초과.

## 판정기 연결과 자동 기준 (2026-10-04)

**판정기:** `DetectorCorrectionJudge`가 한/영 경고의 판정기(`MistypeDetector`, 영문 모드 → 한글 의도 방향)를 고침 정책에 연결한다.
- 수동은 경고용으로 측정한 기본 기준을 그대로 쓴다: 3타 이상, 한국어 점수 −2.75.
- 자동은 사용자의 전환 없이 글자를 바꾸므로 더 엄격하게 4타 이상, −2.75를 쓴다.
- `Tests/perf/mistype-eval.sh --max-fp 0.1`로 쟀다(전체 표는 `data/0064-mistype-eval.md`).

| 설정 | 검출 (뉴스 / 대화체) | 오탐 /1000단어 (뉴스 / 위키 / 코드) |
|---|---|---|
| 수동 (3타, −2.75) | 97.1% / 92.9% | 0.02 / 0.03 / 0.16 |
| 자동 (4타, −2.75) | 93.8% / 87.5% | 0.01 / 0.01 / 0.08 |

- 도구는 4타, −3.00을 추천했다. 검출은 거의 같고(93.8% / 87.8%) 뉴스·위키 오탐이 세 배(0.03)여서 −2.75를 골랐다.
- 코드 오탐은 `workdir`와 저장소의 `dkssud` 예시였다.

**측정 도구 수리:** 판정기가 `InputMethodIntegration`을 참조한 뒤로 측정 도구 빌드가 깨져 있었다. KeyHueCore 전체를 함께 컴파일하도록 고쳤다. 코드 말뭉치에서는 일부러 영문으로 친 한글을 담은 입력기 Core·host 테스트를 뺐다.

**입력기 번들:**
- 설치본은 `~/Library/Input Methods`에서 앱과 따로 실행되므로 판정 모델과 CC BY-SA 라이선스를 직접 가진다. [ADR 0046](0046-shared-component-build-and-imk-spike.md)의 "기술 검증 번들에는 판정 모델을 넣지 않는다"를 대체하며, `check-bundle.sh`는 이제 둘이 없으면 실패한다.
- 영어 사전(`SystemEnglishLexicon`, NSSpellChecker)은 유틸리티와 입력기가 함께 쓰도록 `KeyHueSystemLexicon` 모듈로 옮겼다.
- 입력기는 고침 대상 클라이언트가 처음 활성화될 때 모델을 백그라운드에서 읽는다. 측정 242ms였다. 준비 전 결정은 `detectorNotReady`로 남는다.

**IMK 연결부(`IMKManualCorrection`):**
- 정책의 결정을 받아 원문, 커서, 조합 상태를 확인한 뒤 교체한다. 결과(`corrected`·`expired`·`lost-context`)와 생략 이유(`CorrectionSkip.logName`)만 서버 로그에 남긴다.
- 아직 전용 테스트 앱 ID에서만 동작한다.

**실제 판정기 결과 (`20261004-111446/`):**
- `dkssudgktpdy ` → `안녕하세요 `, `gksrmf` → `한글`이 네 전환 경로 모두에서 고쳐졌다. 앱 안 전환에서는 되돌리기로 원문이 복원되고 한글 모드가 유지됐다.
- `hello `와 `keyboard`는 `notMistyped`로 남았다.
- 같은 전환의 두 번째 신호는 `duplicateSignal`로 기록됐다.

**이유 로그로 찾은 버그:**
- 연결부는 단어를 추적 중이 아닐 때만 단어 시작을 확인한다. 그런데 Space로 끝난 단어도 "추적 중"으로 보고 있었다.
- 그래서 `hello dkssud`처럼 두 번째 단어가 `dropped.notAtWordStart`로 버려졌다.
- `isTrackingWord`가 끝난 단어를 제외하도록 고치고 Core 테스트로 고정했다. 수정 뒤 실행(`20261004-112113/`)에서 `hello dkssudgktpdy` → `hello 안녕하세요`로 두 번째 단어만 고쳐졌고, 나머지 결과도 위와 같았다. 대조군의 이유는 다음과 같다: 새 짧은 단어 `r`은 `notMistyped`(최소 타수 미달), 커서 이동은 `dropped.interrupted.cursorMoved`. 그 전 두 번의 실행은 사용 중 포커스 변경으로 중단됐다.

## 설정과 자동 모드 연결 (2026-10-04)

**설정:**
- `KeyHueSettings.inputMethodCorrection`(기본 수동)과 `correctionExcludedApps`(기본: 터미널 7개, 코드 편집기·IDE 14개. [ADR 0067](0067-bidirectional-correction-and-terminals.md)에서 빈 목록과 배포 예외 단어로 바꿨다)를 추가했다. 저장 키는 프로퍼티 이름과 같고, 기본값과 같으면 저장하지 않는다(ADR 0014).
- `CorrectionMode`는 유틸리티와 입력기가 함께 쓰도록 KeyHueCore로 옮겼다.
- 입력기는 별도 프로세스라서 유틸리티의 설정 도메인(`io.github.sejoung.keyhue`)을 `InputMethodCorrection.read`로 같은 규칙에 따라 읽는다. 읽는 시점은 고침 대상 클라이언트가 처음 활성화될 때와, 설정이 바뀌어 유틸리티가 `…correction-settings-changed` 알림을 보낼 때다.
- 서버 로그에는 모드와 제외 앱 수만 남긴다.

**설정 화면:**
- "실험적 · 단어 고침" 절에서 끄기, 한글로 바꿀 때(수동), Space에서 자동으로를 고른다. "고치지 않는 앱" 목록에서 앱을 추가·제거하고 기본값으로 되돌릴 수 있다.
- 입력기를 사용할 때만 편집할 수 있다.
- 설명에는 "지금은 KeyHue가 확인한 앱에서만 동작"을 적었다.
- 문구는 영어·한국어·일본어로 번역했다.

**테스트의 모드:** 테스트가 사용자 설정을 바꾸지 않도록 테스트 앱 ID마다 모드를 고정한다. 수동 테스트 앱은 수동, 자동 테스트 앱은 자동이다. 제외 목록과 보안 입력(`IsSecureEventInputEnabled`)은 실제 값을 쓴다.

**자동 모드:**
- `CorrectionPolicy`(자동, 4타 기준 판정기)가 Space에서 결정하고, 검증된 단계별 교체 엔진 `CorrectionProbe`가 실행한다(ADR 0056·0057).
- 엔진은 더 이상 `dkssud`만 받지 않고 정책이 넘긴 단어와 결과를 실행한다. 엔진의 "고정 단어만" 테스트는 정책 테스트(식별자·URL·기호 단어는 후보 아님)와 판정기 테스트(`hello`·`API` 유지)로 옮겼다.
- 엔진이 직접 요청한 모드 변경이 아닌 외부 신호는 정책에도 전달해 되돌리기를 취소한다(ADR 0058).

**검증:**
- Core·앱 단위 테스트를 먼저 작성해 실패를 확인한 뒤 구현했다: 설정 기본값·저장·복원·깨진 값·입력기 읽기 규칙, 제외 목록 편집, 엔진의 임의 단어.
- 실제 테스트 앱 검사(자동·수동)의 첫 시도는 화면 잠금으로 시작하지 못했다. 맨 앞 앱이 `loginwindow`였다.

**실제 테스트 앱 검사와 고친 버그:**
- 첫 실행(`20261004-114740/`): 수동은 모두 통과했다. 자동은 "고침 직후 빠른 되돌리기"에서 실패했다. 원인은 두 가지가 겹친 것이었다.
  - 직전 경우에서 Space 직후 Backspace로 교체 전에 취소된 고침이 정책에는 남아 있었다. 정책은 그것을 되돌림으로 처리하고 단어를 계속 추적했다.
  - 문서가 비워진 뒤 새 단어의 커서가 건너뛰었는데도, 연결부가 "추적 중"이라는 이유로 단어 시작 확인을 하지 않았다.
- 고친 것:
  - 교체 전에 취소된 고침은 정책에서도 지운다.
  - 정책이 단어 시작 확인(클라이언트 조회)을 새 단어이거나 커서가 건너뛰었을 때만 연결부에 묻게 했다(`atWordStart`를 지연 평가). `theWordStartIsAskedOnlyWhenNeeded`로 고정했다.
- 수정 후:
  - 자동(기존 경합·필드 이동·외부 선택 검사 전체)이 두 번 연속 통과했다(`115036/`, `115105/`).
  - 수동도 통과했다(`114955/`).
- 수정 직후 첫 자동 실행은 KeyHue 한글 첫 글자 조합 단계에서 실패했다. 재설치 직후라 실행 동안 입력기 서버가 시작된 기록이 없었고, 서버는 다음 실행에서야 시작됐다. 고침과 무관한 콜드 스타트 문제로 기록만 남긴다(ADR 0061·0062 영역).

## 일반 앱 허용 (2026-10-04)

**경로 결정(`CorrectionRouting`, Core):** 어느 클라이언트를 어떤 모드로 고칠지 정한다. 경로가 없는 클라이언트는 고침 경로에 아예 들어가지 않는다. 단어 추적, 클라이언트 조회, 로그가 모두 없다.
- 테스트 앱 → 고정 모드
- 사용자 제외 앱 → 없음. 테스트 전용 값보다도 우선한다.
- 교체를 실제로 확인한 앱(`verifiedApps`, 처음에는 TextEdit) → 사용자 설정의 모드. 끄기면 없음.
- 그 밖의 앱 → 없음
- 입력기의 키 단위 진단 로그는 자동 테스트 앱에서만 남긴다.

**테스트 전용 값:**
- 실제 앱 검사는 사용자 설정을 바꾸지 않는다. 대신 입력기 자신의 설정 도메인에 `correctionModeTestOverride = "<모드>@<만료 시각>"`을 쓴다.
- 이 값은 만료 전이고 지금부터 15분 이내일 때만 유효하다. runner가 비정상 종료해도 오래 남지 않는다. runner는 끝날 때 값을 지우고 입력기에 다시 읽게 한다.
- TextEdit runner는 고침 검사가 아닐 때 `off`를 써서, 기존 검사가 사용자 설정과 무관하게 같은 결과를 내게 한다.
- 사용자가 TextEdit을 제외했으면 고침 검사를 거부한다.

**결과:**
- TextEdit에서 실제 키와 판정기로 수동 5개 사례(`20261004-115845/`), 자동 5개 사례(`115946/`)가 통과했다. 사례 목록은 [호환성 기록](../INPUT_METHOD_COMPATIBILITY.md)에 있다.
- 꺼진 상태의 일반 회귀 32개도 통과했다(`120056/`).
- 다른 앱(Notes, 브라우저, Electron 등)은 같은 검사를 통과한 뒤 `verifiedApps`에 추가한다.

## 결과

- 사용자는 자동 교체를 받아들이지 않고도 평소의 한/영 전환만으로 고침을 쓸 수 있다.
- 수동 모드는 입력기가 외부 전환 직후 직전 단어를 안전하게 교체할 수 있다는 가정에 기댄다. 1단계 실험에서 이 가정이 깨지면 수동 신호를 바꿔야 한다. 예를 들어 입력기가 직접 처리하는 별도 키를 쓸 수 있다.
- 세션 없는 클라이언트의 외부 선택(ADR 0061)처럼 입력기가 모드 변경을 받지 못하는 경우에는 수동 고침도 일어나지 않는다. 사용자의 전환이 같은 앱 안에서 처리되면 세션이 있으므로 대부분의 수동 경로는 영향이 없다.
- ADR 0045의 "자동 고침은 기본 OFF"는 이 결정으로 대체한다. 고침 기본값은 수동이고, 자동은 사용자가 고른다.
