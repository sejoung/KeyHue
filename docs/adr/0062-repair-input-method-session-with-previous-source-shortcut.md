# 0062. 입력기 세션이 확인되지 않으면 사용자의 이전 입력 소스 단축키를 두 번 누른다

상태: Accepted (Core·유틸리티 구현, 실제 TextEdit 새 클라이언트·서버 재시작 검사 통과. 2026-10-05 거짓 확인 보완)

날짜: 2026-10-04

관련: [0049](0049-opt-in-input-method-integration.md), [0061](0061-external-selection-does-not-open-input-method-session.md)

## 배경

[ADR 0061](0061-external-selection-does-not-open-input-method-session.md)에 따라 다른 프로세스의 TIS 선택은 아직 세션이 없는 클라이언트에 KeyHue 입력기 세션을 만들지 않는다. 유틸리티의 자동 전환(앱 전환·ESC·필드 이탈·앱별 기억·ABC 연동)도 같은 선택을 사용하므로 로그인·업데이트·서버 재시작 직후 첫 입력이 원시 ASCII가 될 수 있다. 입력 메뉴와 `⌘Space`는 클라이언트 프로세스 안에서 선택을 처리해 세션을 만든다.

같은 선택 뒤 테스트 helper가 설정된 이전 입력 소스 단축키(시스템 항목 60)를 HID 경로로 두 번 보냈다. 소스는 `한글 → ABC → 한글`로 돌아왔고 TextEdit이 서버를 실행·활성화했다. 새로 실행한 TextEdit(`20261004-005741`, 50ms 간격 `005904`)과 서버 재시작 뒤 세 번(`005801`)이 모두 통과했다. 자료는 `.artifacts/input-method-textedit/`에 있다.

## 결정

- 입력기 서버는 distributed notification(`InputMethodIntegration.sessionAcknowledgement`)을 즉시 전달로 보낸다. 객체는 모드 ID뿐이며 클라이언트·문서·키 정보는 보내지 않는다. 보내는 경우는 다음과 같다(`SessionAcknowledgement`).
  - 클라이언트 세션의 활성화가 받아들여졌을 때.
  - 모드 callback을 처리했을 때. 요청된 ID를 보낸다. callback이 TIS 반영보다 먼저 오면 세션 모드는 아직 이전 모드이기 때문이다.
  - 앞 앱 클라이언트의 활성 세션이 입력 소스 변경 알림을 받았을 때. 다른 프로세스가 이 서버의 두 모드 사이를 선택하면 기존 세션에는 callback 없이 이 알림만 온다.
- 유틸리티가 자기 전환기로 KeyHue 한글·영문을 선택해 소스가 바뀌면 250ms 동안 그 모드의 확인을 기다린다(`InputMethodSessionRepair`). 확인이 오면 아무것도 하지 않는다.
- 확인이 없으면 사용자가 켜 둔 이전 입력 소스 단축키를 50ms 간격으로 두 번 누른다. 첫 번째는 이전 소스로, 두 번째는 목표 모드로 돌아오며 앞 앱이 자기 프로세스에서 선택한다. 최종 소스는 바뀌지 않는다. 단축키 설정은 읽기만 하고 수정하지 않는다.
- 선택마다 한 번만 시도한다. 누른 뒤 250ms 안에도 확인이 없으면 그 앱(PID)에는 다시 시도하지 않는다. 텍스트 입력 문맥이 없는 앱에서 앱을 바꿀 때마다 단축키를 누르지 않기 위한 제한이다.
- 다음 경우에는 누르지 않는다: 기다리는 동안 사용자의 키·클릭, 앞 앱 변경, KeyHue 자신이 앞 앱, 보안 입력(`IsSecureEventInputEnabled`), 이벤트 전송 권한 없음, 단축키가 꺼져 있거나 수식 키가 없는 형태. Caps Lock·Fn 전환은 단축키가 아니므로 합성하지 않는다.
- 보내는 이벤트에는 표식(`eventSourceUserData`)을 넣고 KeyHue의 listen-only 탭은 이를 사용자 입력으로 보지 않는다. 복구 중 선택 알림은 상태·앱별 기억·ABC 연동에 반영하지 않고, 끝난 뒤 실제 TIS를 다시 읽어 기준을 세운다. 시작할 때 자동 전환의 대기 작업은 취소한다.
- ADR 0049의 "키를 차단·재전송하지 않는다"는 사용자 입력에 대해 유지한다. 이 결정은 사용자 키가 아닌 시스템 전환 단축키를 위 조건에서만 보내는 예외다. 입력 문자열을 읽거나 저장하지 않는다.
- 진단과 opt-in 검사를 위해 같은 구성(`SystemSessionRepair`)을 쓰는 worker 명령 `--keyhue-select-input-source-repairing <id>`를 둔다. 서버 확인을 놓치지 않도록 선택 전에 수신을 등록하고, 결과 이름만 출력한다.

## 검증과 한계

Core 판단은 `InputMethodSessionRepairTests`가 가짜 시간으로 검사한다: 확인 시 생략, 두 번 누름, 같은 앱 재시도 금지와 다른 앱 허용, 상호작용 취소, 복구 중 상호작용·선택 무시, 모드 일치, 대상이 아닌 선택, 단축키 불가·앞 앱 변경 생략, 새 선택의 대체, 첫 누름 실패 시 두 번째 생략. 단축키 설정 해석은 `InputSourceShortcutTests`, worker 인자는 `WorkerCommandTests`가 검사한다.

서버의 확인 판단은 `SessionAcknowledgementTests`가 검사한다: 요청 ID 확인, 다른 소스 무시, 활성·앞 앱 세션만 선택 변경 확인.

실제 TextEdit 검사는 `KEYHUE_TEST_TEXTEDIT_MODE_SWITCH=repair`로 실행한다. 2026-10-04 첫 두 실행은 화면 잠금으로 테스트 창을 열지 못해 결과가 없다(`010717`, `010725`). 이후 결과는 다음과 같다(서비스 0.2.5·빌드 77, `.artifacts/input-method-textedit/`).

| 경우 | 결과 | 근거 |
|---|---|---|
| 새로 실행한 TextEdit, 새 서버 | 통과: 한글 선택 `repaired`, 첫 `d → ㅇ`·`안`·`안a ` | `20261004-092705/` |
| 메뉴 준비한 TextEdit, 서버 재시작(첫 서버 수정 전) | 1·2회 통과. 세션이 있는 상태의 한글→영문 선택이 확인 없이 `unrepaired`로 끝났다. 3회차 준비의 메뉴 ABC 선택 뒤 ABC가 아니어서 중단 | `20261004-092723/` |
| 메뉴 준비한 TextEdit, 서버 재시작(서버 확인 보완 후) | 세 번 통과: 매회 한글 `repaired`, 영문 전환 `acknowledged`(단축키 없음) | `20261004-093143/` |
| 새로 실행한 TextEdit, 새 서버(보완 후) | 통과: 한글 `repaired`, 영문 `acknowledged` | `20261004-093254/` |
| 일반 메뉴 회귀(입력 기본·조합·창 왕복) | 통과 | `20261004-093310/` |

보완 전 실행에서 서버는 외부의 모드 간 선택을 받은 기존 세션에서 확인을 보내지 않았다. 누른 뒤의 callback에서도 아직 동기화되지 않은 세션 모드(한글)를 보냈다. 유틸리티였다면 TextEdit이 재시도 금지 앱이 되어 이후 서버 재시작에서 복구되지 않았을 것이다. 위 결정의 요청 ID 확인과 선택 변경 확인으로 고쳤다. 3회차 준비 실패는 같은 조건의 다음 실행에서 재현되지 않았다. 원인은 확인하지 못했다.

확인 기한은 서버가 클라이언트에 의해 새로 실행되는 시간보다 짧을 수 있다. 그 경우 필요 없는 복구가 일어나지만 최종 소스는 같다. 복구 중 macOS 입력 소스 표시가 잠깐 보일 수 있다. 사용자가 이전 입력 소스 단축키를 끄거나 Caps Lock만 쓰면 ADR 0061의 제약이 그대로 남는다. 입력 모니터링 권한이 없어 키보드 탭이 꺼져 있으면 기다리는 동안의 입력을 알 수 없어 취소하지 못한다. TextEdit 외 앱·다른 OS는 별도 검사 대상이다.

## 보완 (2026-10-05): 닫히는 세션의 거짓 확인

- 증상: Ghostty에서 `⌘Space`로 바꾸자(KeyHue 영문 → ABC → 유틸리티가 KeyHue 한글로 넘김) 한글 모드인데 영문이 입력됐다. 유틸리티는 복구하지 않았다.
- 원인: 입력 소스 변경 알림이 닫히는 세션의 `deactivateServer`보다 먼저 올 수 있다. 그 세션은 아직 활성이고 앞 앱의 클라이언트라서 새 모드(한글)를 확인으로 보냈다. 실제로는 한글 세션이 열리지 않았는데 유틸리티는 확인을 받아 복구를 건너뛰었다. 입력기 로그에서 비활성화 직전에 같은 세션이 한글을 보는 기록으로 확인했다.
- 결정: 선택 변경 확인은 `SessionAcknowledgement.selectionChangeDelay`(80ms) 뒤에 활성·앞 앱 조건을 다시 보고 보낸다. 유틸리티의 기한(250ms)의 절반 안이다. callback(활성화·모드)으로 보내는 확인은 그대로 즉시 보낸다.
- 검사: `SessionAcknowledgementTests`가 지연이 기한 안에 있음을 확인한다. TextEdit 진입 복구 검사(서버 재시작, `repair`) 세 번 통과(`.artifacts/input-method-textedit/20261005-132422/`).
