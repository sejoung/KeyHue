# 0068. 단어 고침은 사용자가 단축키로 요청할 때 한다

- 상태: Accepted (구현·단위 테스트·TextEdit·Ghostty 실제 검사 완료)
- 날짜: 2026-10-04
- 관련: [0064](0064-correction-modes-off-manual-automatic.md), [0065](0065-correct-all-apps-with-feedback.md), [0067](0067-bidirectional-correction-and-terminals.md)

## 배경

[ADR 0064](0064-correction-modes-off-manual-automatic.md)·[0067](0067-bidirectional-correction-and-terminals.md)의 수동 고침은 단어 직후 한/영을 바꾸면 고쳤다. 사용자는 이렇게 지적했다.

- 고침이 한/영 전환에 묶여 있어 원할 때 쓸 수 없다. 이미 바꾼 뒤에는 고칠 수 없다.
- 단어를 키로 추적하다가 조용히 후보에서 뺀다. 그래서 원해도 안 될 수 있다. 다음 경우가 그렇다:
  - 다른 키, 커서 이동, 두 번째 Space
  - 판정기가 영어로 본 단어
  - 같은 모드로의 신호
- 무엇이 제외되는지 사용자가 알 수 없다.

## 결정

### 단축키로 요청
- 수동은 **단축키를 누를 때** 고친다. 한/영 전환은 더 이상 고침 신호가 아니다.
- 단축키는 설정에서 고른다(`KeyHueSettings.correctionShortcut`, 기본 ⌥↩). 입력기가 직접 받는 키라서 다음 조합만 허용한다(`CorrectionShortcut.isAllowed`):
  - ⌥나 ⌃와 함께 누르는 키
  - ⇧Space, ⇧Return
- 다음 키는 허용하지 않는다:
  - ⌘ 조합: 앱 메뉴가 먼저 가져가서 입력기까지 오지 않을 수 있다.
  - 수정키 없이 누르거나 ⇧와 함께 누르는 글자 키: 글자를 입력한다.
  - ⌃Space, ⌃⌥Space: 시스템 입력 소스 단축키다.
- 다른 앱의 전역 단축키(Raycast·Alfred의 ⌥Space 등)와 겹치면 입력기까지 오지 않는다. 사용자가 다른 키를 고른다.

### 무엇을 고치나
- 선택 영역이 있으면 선택 영역을 고친다. 없으면 커서 바로 앞 단어를 고친다.
  - 커서 바로 앞의 Space·Tab은 건너뛰고 그대로 둔다(방금 Space로 끝낸 단어).
  - 그다음 공백까지를 한 단어로 본다. 줄바꿈은 건너뛰지 않는다.
- 요청한 순간 앱에서 글자를 읽어 고친다(커서 앞 128자). 키를 추적하지 않으므로 중간에 후보에서 빠지는 일이 없다.
- **판정기를 쓰지 않는다.** 사용자가 요청했으므로 무엇이든 바꾼다(`hello` → `ㅗ디ㅣㅐ`). 예외 단어와 되돌린 단어도 단축키에는 적용하지 않는다.
- 변환 규칙(`LayoutConversion`):
  - 방향: 마지막 글자가 영문이면 한글로, 한글이면 영문으로.
  - 글자 덩어리: 영문·한글 글자가 이어진 부분을 친 키로 되돌린 뒤 대상 모드로 다시 읽는다.
  - 숫자·문장 부호: 그대로 둔다.
- 고친 뒤 고친 언어로 입력 모드를 바꾼다.
- 바로 단축키를 한 번 더 누르면 정확히 원래 글자와 원래 모드로 되돌린다(`ShortcutToggle`). 다른 키나 클릭이 오면 새 요청이 된다.
- 교체 후 화면의 글자를 확인한다. 앱이 무시하거나 결과가 다르면 실패로 알린다(ADR 0065).

### 터미널
- 터미널은 글자를 읽을 수 없다. 그래서 입력기가 터미널에서만 마지막 단어를 키로 기억한다(`TypedWord`).
  - 단어는 공백 뒤로 친 키이고, 한글 모드 부분은 조합된 글자로 본다.
  - 단어 뒤의 Space는 함께 기억한다.
  - Backspace는 조합 중이면 키 하나, 아니면 한 글자를 지운다.
  - Return·Tab·방향키·다른 키·클릭에서는 비운다.
- 지우고 넣는 방식은 ADR 0067과 같다(Backspace 키, 입력기 손쉬운 사용 권한). 단축키의 수정키를 뗀 뒤에 보낸다.
- Ghostty는 입력기가 받은 키도, 조합 중인 글자가 없으면 프로그램에 보낸다(⌥↩ → `ESC Return`). 그러면 셸이 글자를 하나 더 넣어 Backspace가 하나 모자란다. 사용자가 `ㅁㄴㅇ` 뒤 Space를 치고 고쳤을 때 `ㅁasd`가 된 원인이다. 그래서 확정할 글자가 없으면 그 키를 처리하는 동안 폭 없는 자리표시(U+200B)를 조합 중으로 두고 키가 끝나면 지운다(`DetachedCommit.consume`). 자리표시는 확정되지 않는다. 확정할 글자가 있으면 Ghostty는 키 대신 그 글자를 보내므로 그대로 둔다.

### 명확한 제외 규칙
단축키가 고치지 않는 경우는 다음뿐이다.
- 고침 끄기, "고치지 않는 앱": 단축키가 그 앱에 그대로 간다.
- 비밀번호 칸: 입력기가 키를 받지 않는다.
- 고칠 글자 없음(커서 앞에 단어가 없고 선택도 없음): "고칠 단어가 없습니다"를 보인다(`CorrectionFailure.nothingToFix`). 앱 탓이 아니므로 "고치지 못한 앱"에는 기록하지 않는다.
- 앱이 글자를 알려 주지 않음, 교체를 무시함, 결과가 다름, 터미널 권한 없음: 이유를 보이고 ADR 0065대로 기록한다.

### 자동 모드
- "단축키와 Space에서 자동으로"는 단축키에 더해, 영문으로 친 한글 단어를 판정기가 실수로 보면 Space에서 고친다(ADR 0064의 자동, 예외 단어·되돌린 단어 적용). 바로 Delete로 되돌린다.
- 터미널은 자동으로 고치지 않는다(ADR 0067).

### 설정 화면
- 선택지는 "끄기 / 단축키로 / 단축키와 Space에서 자동으로"다. 저장 값(`off`·`manual`·`automatic`)은 그대로다.
- "고침 단축키" 칸을 누른 뒤 키를 누르면 바뀐다. Esc는 취소다. 허용하지 않는 키는 안내와 함께 거절한다.
- "고치지 않는 단어"와 "되돌린 고침 기록"은 판정기에만 쓰이므로 자동을 고를 때만 보인다(`SettingsModel.showsDetectorOptions`). 저장된 값은 그대로 둔다. "고치지 못한 앱"은 단축키에도 쓰이므로 늘 보인다.

## 결과

- 사용자는 언제든, 어느 방향이든, 판정과 상관없이 고칠 수 있다. 같은 키로 되돌린다.
- 한/영 전환으로 고치던 동작과 그 실험 검사(`KEYHUE_TEST_MANUAL_PROBE`)는 없앴다. 결과는 ADR 0064에 남아 있다.
- 수동에서 판정기와 키 추적이 빠지면서 수동 경로의 조용한 제외가 없어졌다.
- 입력기가 받는 키가 하나 늘어난다. 고침이 켜진 앱에서는 그 키가 앱에 가지 않는다.

## 검사

- 단위 테스트(먼저 작성해 실패 확인):
  - `CorrectionShortcutTests`: 기본값 ⌥↩, 저장 형식, 잘못된 값, 허용 규칙, 표시, 일치, 설정 저장·복원·기본값 미저장·입력기 읽기
  - `ShortcutCorrectionTests`: 양방향 변환, 판정기 없음, 방향, 섞인 글자와 문장 부호, Shift 자음, 커서 앞 단어(뒤 Space, 줄바꿈, 잘린 단어, UTF-16), 되돌리기, 터미널 단어(섞인 모드, Space, 비우기, Backspace, 고친 뒤 상태, 계획)
  - `CorrectionPolicyTests`: 자동만 남김. 전환은 고치지 않음, 수동·끄기는 추적하지 않음
  - `CorrectionFeedbackTests`·`CorrectionFeedbackStoreTests`: 고칠 글자 없음은 보이되 기록하지 않음
  - `CorrectionSettingsModelTests`: 예외 단어·되돌린 고침은 자동일 때만 보임
  - `ConsumedKeyTests`: Ghostty에서 확정할 글자가 없을 때만 자리표시를 두고 지움
- 실제 앱 검사:
  - TextEdit(`KEYHUE_TEST_TEXTEDIT_CORRECTION=manual`): 양방향 고침, 다시 눌러 되돌리기, Space로 끝난 단어, 영어도 요청하면 변환, 마지막 단어만, 선택 영역, 고칠 글자 없음, 전환은 고치지 않음
  - Ghostty(`KEYHUE_TEST_GHOSTTY_CORRECTION=1`): 위와 같은 흐름을 바이트로 확인
  - 두 runner 모두 사용자의 단축키가 기본값(⌥↩)일 때만 실행한다.

결과 (2026-10-04):

- TextEdit 단축키 13개 사례 통과(`.artifacts/input-method-textedit/20261004-224829/`). 첫 실행은 테스트 키 도구가 ⌥ 키를 허용하지 않아 시작하지 못했고, 도구를 고친 뒤 통과했다.
- TextEdit 자동 7개 사례 회귀 통과(`20261004-224956/`). Ghostty 기본 입력(ADR 0066) 회귀 통과(`input-method-ghostty/20261004-225025/`).
- Ghostty 터미널 고침은 사용자의 "고치지 않는 앱"에 Ghostty가 있고 입력기 권한이 없어 아직 실행하지 않았다.

결과 (2026-10-05):
- 사용자가 Ghostty에서 `ㅁㄴㅇ`을 고치면 `ㅁasd`가 된다고 알렸다. TextEdit에서는 재현되지 않았다(홑자모 2개 사례 추가, 15개 통과, `.artifacts/input-method-textedit/20261005-122024/`).
- Ghostty 고침 검사를 처음 돌리자 모든 고침이 "수정키를 누르고 있음"으로 만료됐다. 검사 키 도구가 ⌥를 누른 채 떼지 않았다. 실제 키보드처럼 수정키를 누르고 떼도록 고쳤다.
- 그 뒤 위 원인(단축키가 셸에 감)이 바이트로 보였다(기본 `\x1b\r`, kitty `\x1b[13;3u`). 자리표시로 고친 뒤 기본·kitty 각각 고침 6개 사례를 포함해 전부 통과했다(`.artifacts/input-method-ghostty/20261005-123146/`). 추가한 사례: 홑자모, Space로 끝난 단어(단축키가 셸에 가지 않음).
- `scripts/verify.sh` 통과(입력기 Core 172, Core 574, 앱 276, 스크립트 115).
- 검사 중 "Allow Ghostty to execute …?" 창이 계속 떴다. 테스트 창을 `-e /usr/bin/python3 <스크립트> <기록 파일>`로 열면 AppKit이 실제 파일 경로인 인자를 "파일 열기"로 넘기고, Ghostty가 파일마다 실행 허락을 묻는다. 경로가 아닌 인자 하나(`--initial-command=direct:…`)로 바꿨고, 창 없이 한 번에 통과했다(`.artifacts/input-method-ghostty/20261005-125011/`). 앞서 테스트 창이 포커스를 놓친 일도 이 창 때문으로 보인다.
