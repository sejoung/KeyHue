# 0071. 라우팅은 떠나는 모드를 먼저 선택하고, 터미널 고침은 수정키를 뗄 때까지 기다린다

상태: Accepted (구현·단위 테스트, Ghostty 실제 전환·고침 검사 통과)

날짜: 2026-10-06

관련: [0062](0062-repair-input-method-session-with-previous-source-shortcut.md), [0068](0068-fix-words-with-a-shortcut.md), [0070](0070-acknowledge-only-open-sessions-and-retry-repair.md)

## 배경

ADR 0070 설치 뒤 사용자 보고(Ghostty):

- 단축키로 한/영을 바꾸면 딜레이가 크다.
- `asd`를 치고 ⌥↩를 누르면 "고칠 단어가 없습니다"가 뜬다. 사용자가 요청하면 무조건 바꿔야 한다.

사용자의 전환 키는 ⌘Space다(시스템 항목 60, "이전 입력 소스 선택"). 2026-10-06 10:28 전후 `KeyHue.log`·`KeyHueInputMethod.log`(빌드 96)를 맞춰 본 결과는 다음과 같다.

**전환 딜레이: ABC를 거치는 순환**

- 입력기 설치는 ABC를 선택한 뒤 KeyHue 한글을 선택한다. 그래서 "이전 입력 소스"가 ABC가 된다.
- ⌘Space → ABC(클라이언트 안 선택) → 라우팅이 KeyHue 영문을 외부 선택 → Ghostty가 세션을 1ms 안에 닫음(ADR 0070) → 250ms 뒤 복구가 ⌘Space를 두 번 누름.
- 10:28:06.841 선택부터 10:28:07.401 세션 활성화까지 0.56초가 걸렸다. 그동안 친 키는 입력기를 거치지 않았다.
- 라우팅의 외부 선택은 이전 소스를 ABC로 남긴다. 그래서 다음 ⌘Space도 ABC로 가고, 같은 경로가 전환마다 반복될 수 있다. 09:38~09:40에는 전환마다 ABC를 거쳤다.
- 같은 날 KeyHue 모드끼리 바로 오간 ⌘Space 전환(10:28:33 이후)은 유틸리티 알림과 같은 ms에 mode callback이 왔다. 입력기 쪽 지연은 없었다.

**`asd` ⌥↩ → 고칠 단어 없음**

- 터미널은 글자를 알려 주지 않는다. 그래서 입력기가 받은 키로만 단어를 안다(`TypedWord`, ADR 0068).
- 10:28:07.528의 첫 실패: 세션이 닫힌 사이 친 `asd`는 입력기에 오지 않았다. ⌥↩가 세션이 다시 열린 직후(07.526) 처음 받은 키였다.
- 같은 로그에 `already waiting` 뒤 `result=expired reason=modifiers held`가 세 번 있었다. 터미널 고침은 ⌥를 뗀 뒤에 Backspace를 보낸다. 떼기 전에는 아무 변화가 없어서 사용자는 ⌥를 누른 채 ↩를 다시 눌렀다. 1초가 지나면 고침이 조용히 사라졌다.
- 그 뒤 연속된 "고칠 단어 없음"에서 기억한 단어를 무엇이 비웠는지는 로그로 알 수 없었다.

## 결정

- **떠나는 모드를 먼저:** 라우팅(ABC → KeyHue 모드)은 목표 모드 직전에 떠나는 모드를 선택한다(한글 → ABC면 한글, 영문). 이렇게 하면 이전 입력 소스가 ABC가 아니라 떠난 모드가 된다. 다음 ⌘Space는 클라이언트 안에서 두 모드를 바로 오가고, 라우팅·외부 선택·세션 복구를 다시 거치지 않는다. 그 사이의 알림(떠나는 모드)은 사용자의 새 선택으로 보지 않는다. 그 직후의 ABC는 목표 직후와 같이 덮어쓰기로 보고 라우팅을 멈춘다.
- **설치 직후:** 입력기 설치·설정 완료 뒤 KeyHue 한글을 고르기 전에 KeyHue 영문을 먼저 선택한다. 첫 ⌘Space부터 두 모드를 오간다.
- **수정키 대기:** 터미널 고침은 수정키를 누르고 있는 동안 10초까지 기다린다(이전 1초). ⌥를 누른 채 ↩를 다시 눌러도 같은 요청이고(`PendingKeyFix`), ⌥를 떼면 고친다. 조합 중인 글자를 기다리는 한도는 1초 그대로다.
- **터미널 안내:** 터미널에서 고칠 단어가 없으면 "터미널에서는 입력기가 받은 글자만 고칠 수 있습니다. 단어를 다시 친 뒤 단축키를 누르세요."를 보인다. 글자를 읽는 앱의 안내(커서 위치·선택)는 그대로다. 기록하지 않는 것도 같다(ADR 0068).
- **화면 잠금:** 앞 앱이 로그인 창(`com.apple.loginwindow`)이거나 보안 입력이 켜져 있으면 ABC를 라우팅하지 않는다(`InputMethodIntegration.routesABC`). 로그인 창은 ABC를 직접 고르고, 라우팅하면 곧바로 ABC로 되돌린다. 라우팅은 이것을 시스템 덮어쓰기로 보고 사용자의 ABC 연결 옵션을 껐다. 2026-10-06 10:12:21과 10:53:32에 화면을 잠글 때마다 그랬다. 옵션이 꺼지면 ⌘Space가 다시 KeyHue 모드와 ABC를 오간다. 이번 보고의 "고쳤는데 다시 나타남"의 원인 중 하나다.
- **진단:** 터미널 단어가 비어 있으면 입력기 로그에 마지막으로 비운 이유와 그 뒤 받은 키 수를 남긴다(`cleared=activation|click|deactivation|boundary key|… keys=N`). 글자는 남기지 않는다. `keys=0`이면 키가 입력기를 거치지 않은 것이다.

## 결과

- ABC가 이전 소스로 남는 순환이 끊기면, ⌘Space 전환은 외부 선택 없이 클라이언트 안에서 끝난다. 이것이 0.5초 딜레이와 그 사이 놓친 키의 원인이었다.
- 라우팅 한 번에 외부 선택이 두 번이다. 떠나는 모드는 이미 그 모드였으므로 화면 표시는 그대로이고 목표로 바뀐다.
- 이 결정은 외부 TIS 선택이 "이전 입력 소스" 기록에 들어간다는 관찰에 기대고 있다. 09:38:57의 외부 영문 선택 뒤 ⌘Space가 ABC로 간 순서와는 맞지만, HIToolbox의 기록 규칙을 직접 확인하지는 못했다. 그렇지 않더라도 추가 선택은 같은 모드라서 해가 없다.
- 터미널에서 입력기를 거치지 않은 글자는 여전히 고칠 수 없다. 화면의 글자를 읽을 방법이 없고, 유틸리티가 본 키를 입력기에 보내면 친 글자가 프로세스 밖(distributed notification)으로 나간다. 그래서 하지 않는다. 대신 그런 상황이 생기는 전환 경로를 줄이고, 생기면 다시 치라고 안내한다.
- ⌥를 누르고 있으면 고침이 그만큼 늦다. 누른 채 Backspace를 보내면 앱에 따라 ⌥Backspace(단어 지우기)가 될 수 있어 떼기를 기다리는 방식은 유지한다.

## 이전 검사가 놓친 이유

ABC 연결(ADR 0049)과 그 검사는 이전 소스 문제를 고정한 것처럼 보였다. 실제로는 다음 두 가지 때문에 이 상태를 검사하지 못했다.

- **단위 테스트:** 가짜 전환기로 "ABC 알림 → 반대 모드 선택" 판단만 확인했다. macOS의 이전 입력 소스 기록은 가짜 전환기에 없다.
- **실제 앱 검사:** TextEdit 검사는 매 회차 메뉴로 한글 → ABC를 골라 이전 소스를 맞춘 뒤 시작했다(ADR 0060). 설치나 라우팅이 남기는 실제 기록은 검사 대상이 아니었다. TextEdit은 외부 선택 뒤에도 세션을 유지해 ABC를 거쳐도 드러나지 않았다.

그래서 이번에는 메뉴로 맞추지 않는 Ghostty 검사(`KEYHUE_TEST_GHOSTTY_TOGGLE=1`)를 더했다. 다른 프로세스의 선택으로 기록을 만들고, 유틸리티를 실행한 채 실제 단축키를 누른다.
