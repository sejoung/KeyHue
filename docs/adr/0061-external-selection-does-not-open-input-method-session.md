# 0061. 외부 TIS 선택은 연결되지 않은 클라이언트에 입력기 세션을 만들지 않는다

상태: Accepted (콜드 진입 원인 정정·검사 계약 보완, 제품 우회는 0062)

날짜: 2026-10-04

## 배경

[ADR 0060](0060-input-method-entry-and-cold-start-acceptance.md)은 프로그램 전환의 콜드 진입 실패에서 새 서버가 `activate`와 모드 callback을 받은 뒤에도 키가 오지 않았다고 해석했다. runner는 테스트가 끝난 뒤 원래 입력 소스를 다시 선택하고 그 구간까지 포함한 서버 로그를 `input-method-server.log` 하나로 남겼다. 진단 빌드에 클라이언트 bundle ID를 기록하고 시각을 대조한 결과, 실패 실행의 해당 `activate`는 모두 테스트 문서를 닫은 뒤의 복원 선택에서 생겼다. 서버를 먼저 기동한 `235647`도 첫 키 검사 구간에는 서버 callback이 없었다.

[Squirrel의 진입 방향 보고](https://github.com/rime/squirrel/issues/1162)와 [macism의 임시 창 우회](https://github.com/laishulu/macism)도 외부 선택 뒤 입력기 컨트롤러가 활성화되지 않는 현상을 다룬다. [Ongeul #28](https://github.com/hiking90/ongeul/issues/28)은 선택할 수 없는 부모 항목을 선택한 다른 원인이다. KeyHue는 mode ID를 직접 선택하므로 해당하지 않는다.

## 관찰

macOS 26.6.2 (25G83), arm64, TextEdit 1.20, 서비스 0.2.5·빌드 76(진단 로그만 추가)에서 확인했다. 자료는 `.artifacts/input-method-textedit/20261004-<시각>/`이다.

- 다른 프로세스의 `TISSelectInputSource`가 KeyHue 한글을 선택하고 TIS 조회도 한글을 반환해도, 그 입력기와 세션이 없는 TextEdit은 서버를 실행하거나 연결하지 않았다. 키는 원시 ASCII로 입력됐다. 실행한 적 없는 TextEdit을 ABC로 새로 띄운 경우도 같았다.
- 입력 메뉴는 같은 새 클라이언트·새 서버에서 첫 키 직전에는 서버가 없었지만 TextEdit이 서버를 실행·활성화하고 키를 전달했다.
- 이미 세션이 있는 클라이언트에서는 외부 선택 뒤의 키도 서버로 전달됐다(ADR 0060의 동일 AppKit 앱 `20261003-233305`). 종료된 서버의 세션이 남은 상태에서는 TextEdit의 재연결이 일어난 실행도 있었다(`002937`). 이 경우는 시점에 따라 달라 재현되지 않았다(`003357`).

외부 선택은 클라이언트 프로세스가 이미 가진 입력기 세션만 갱신하고, 새 세션은 문서 활성화나 클라이언트 안에서 처리되는 메뉴·단축키 선택에서 생기는 것으로 판단한다. HIToolbox 내부 구현은 관찰 범위 밖이며 이 결론을 다른 OS·클라이언트로 확대하지 않는다.

## 결정

- 진입 검사는 테스트 구간과 복원 구간의 서버 로그를 나눈다. 클라이언트가 끝나면 그때까지를 `input-method-server.log`, 이후 원래 소스 복원을 `input-method-cleanup.log`로 남긴다. 복원 callback을 테스트 결과의 근거로 사용하지 않는다.
- 첫 키 직전에 서비스 프로세스 존재와 PID를 기록한다. 판정은 계속 실제 문서 문자열로 하며 서버 미실행 자체를 실패로 보지 않는다. 메뉴 경로는 첫 키 직전 미실행 뒤에도 통과한다.
- `KEYHUE_TEST_TEXTEDIT_FRESH_CLIENT=1`은 TextEdit이 실행 중이면 거부하고, ABC를 선택한 뒤 runner가 새로 띄운 TextEdit에서 메뉴 준비 없이 한 번 검사한다. 사용자의 TextEdit을 종료하지 않는다. 서비스가 실행 중이면 같은 조건으로 정상 종료하고, 없으면 그대로 진행한다.
- 서버의 `activate`·`deactivate`·첫 입력 로그에 클라이언트 bundle ID를 남긴다. 입력 글자·키 코드·문서 상태는 남기지 않는다.
- 제품 우회는 이번에 추가하지 않는다. 아래 시도는 모두 해결 근거가 없었다. 키 합성은 기존 연동 계약(입력을 합성하지 않음)을 바꾸는 별도 결정이다. 포커스 왕복은 사용자 화면을 바꾸고 macOS 14 이후 협력적 활성화에서 보장되지 않는다.

| 시도 (모두 AppKit 선택 앱, 임시 변경) | 결과 |
|---|---|
| 새 서버 기동 뒤 ABC를 거쳐 재선택 50ms·1초 간격 (`001609`, `002343`) | 실패, 재선택에도 서버 callback 없음 |
| 서버의 첫 활성화 뒤 `client.selectMode` (`001815`) | 테스트 구간에 활성화가 없어 적용 불가 |
| AX로 포커스 요소 재지정, 해제 후 재지정 (`002639`, `003753`) | 실패, 해제는 `-25201`로 거부 |
| non-activating 패널 키 창 (`002822`) | 실패 |
| 창 없는 활성화, 창 활성화 왕복 (`003128`, `003237`, `003357`) | 실패, 선택 앱은 활성화되지 않음(`active=false`) |
| 같은 왕복 첫 실행 (`002937`) | 세 번 통과했으나 선택 앱은 활성화되지 않았고 재실행 실패. 남은 세션의 재연결로 판단해 근거에서 제외 |

## 결과

| 경로 | 결과 | 근거 |
|---|---|---|
| 새 TextEdit, 새 서버, AppKit 선택 | 실패: 첫 키 직전 서비스 없음, 테스트 구간 TextEdit callback 없음, 복원 활성화는 정리 로그로 분리 | `004319` |
| 새 TextEdit, 새 서버, 입력 메뉴 | 통과: 메뉴 선택 뒤 TextEdit이 서버 실행·활성화 | `004337` |
| 메뉴 준비한 TextEdit, 새 서버, AppKit 선택 | 실패: 정지 뒤 테스트 구간에 새 서버 없음 | `004417` |
| 메뉴 준비한 TextEdit, 새 서버, 입력 메뉴 | 세 번 통과 | `004428` |

`004337`은 통과 뒤 runner의 마지막 `rg` 확인이 이 환경에 없어 127로 끝났다. 두 host runner의 확인을 기본 `grep`으로 바꿨다. 진단 빌드 설치에는 기존 업데이트 검사를 사용했고 원래 입력 소스와 KeyHue 설정 목록을 복원했다.

KeyHue 유틸리티의 자동 전환(앱 전환·ESC·필드 이탈·앱별 기억·ABC 연동)도 같은 외부 선택을 사용한다. 따라서 로그인·업데이트·서버 재시작 뒤 아직 KeyHue 입력기 세션이 없는 앱에서 자동 전환한 직후의 입력은 원시 ASCII가 될 수 있다. 사용자가 앱을 바꾸거나 입력 메뉴·전환 단축키를 사용하면 세션이 생긴다. 이는 알려진 제약이며 유틸리티 자동 연동의 완료 조건으로 남긴다. 사용자 단축키 합성이나 실패 감지 뒤 대체 선택은 별도 ADR에서 결정한다.

후속 [ADR 0062](0062-repair-input-method-session-with-previous-source-shortcut.md)는 서버 확인이 없을 때 사용자의 이전 입력 소스 단축키를 두 번 눌러 클라이언트 안에서 선택하게 한다. 위의 "제품 우회는 추가하지 않는다"는 당시 결정이다.
