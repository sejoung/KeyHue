# 0082. 키로 세션을 확인하고, 시스템이 고른 우회 소스(ABC·시스템 두벌식)를 정리하고, 의심스러운 순간을 로그에 남긴다

- 상태: Accepted (구현·자동 검증·Ghostty 실제 검사·잠금 해제 보완 실제 확인)
- 날짜: 2026-10-07
- 관련: [0062](0062-repair-input-method-session-with-previous-source-shortcut.md), [0070](0070-acknowledge-only-open-sessions-and-retry-repair.md), [0071](0071-route-through-the-leaving-mode-and-wait-for-modifier-release.md), [0036](0036-diagnostic-log.md)

## 맥락

사용자 보고: 가끔 한영 전환이 제대로 안 되는 것 같은데 언제인지 모르겠다. 전환을 눌러도 색이 안 바뀌어 계속 눌렀다.

같은 날 로그에서 두 장면을 찾았다.

- **14:02:43 Chrome, 입력 중 세션 복구**: 자동 전환이 영문을 골랐다. 첫 키가 입력기에 도착해 모드를 맞췄다(43.228). Chrome이 포커스를 옮기며 세션을 닫은 뒤(43.250) 모드 콜백의 확인은 보내지 않았다(0070: 닫힌 세션은 확인하지 않는다). 유틸리티는 확인을 못 받아 이전 소스 단축키를 두 번 눌렀다(43.495). 그 사이 영문 → 한글 → 영문으로 오가서, 친 키가 다른 언어로 들어갈 수 있었다.
- **17:41 카카오톡, 잠금 해제 뒤**: 잠금 화면이 ABC를 골랐다가(17:40:35) macOS가 KeyHue 영문으로 되돌렸다. 0071은 잠금 화면의 ABC를 라우팅하지 않는다. 그래서 ABC가 ⌘Space의 "이전 소스"로 남았다. 첫 전환이 ABC를 거쳐 영문 → 한글로 라우팅됐고(20ms에 세 번 변경), ⌘를 누른 채 Space를 두 번 누르자 그 전 소스인 ABC로 다시 갔다. 결과 모드는 맞았지만 사용자는 4번을 눌렀다. 표시(막대·HUD)는 로그가 없어 색이 실제로 어땠는지 확인할 수 없었다.

## 결정

1. **키가 세션을 확인한다.** 키가 입력기 세션에 도착하면 세션·모드마다 한 번 그 모드 ID를 유틸리티에 알린다(`KeyAcknowledgement`). 활성화 때 다시 알릴 수 있게 비운다. 키가 그 세션에 온 것은 0070이 걱정한 "곧 닫힐 세션"과 달리 실제로 쓰이는 세션이라는 증거다.
2. **시스템이 고른 ABC를 밀어낸다.** 라우팅하지 않은 ABC(잠금 화면·비밀번호 칸)로 KeyHue 모드를 떠났다가 KeyHue 모드 X로 돌아오면, 라우팅이 켜진 상태에서 반대 모드 Y를 고른 뒤 X를 고른다(`InputMethodRoutingCoordinator`). 0071 라우팅과 같은 원리로 이전 소스 기록이 X, Y, ABC 순이 되어 첫 ⌘Space부터 두 KeyHue 모드를 오간다. 키를 치기 시작하면 하지 않는다. 그 전에 ABC로 가서 라우팅됐으면 그것으로 순서가 맞으므로 하지 않는다. 한 번만 한다. 기준선 재설정이 이미 돌아온 모드를 읽었어도 다음 알림에서 한다. KeyHue가 잠금 화면에서 시작돼(업데이트·재실행) 처음부터 ABC를 본 경우도, 라우팅이 꺼진 상태의 ABC로 기준선을 잡으면 같은 대상으로 기억한다(17:59 검사 중 재실행에서 발견).
   - **시스템 두벌식도 같다(우회 소스).** 연동 중에는 ABC와 시스템 두벌식(`detourIDs`)이 모두 KeyHue 모드로 가는 길목일 뿐이다. 시스템 두벌식을 KeyHue 모드에서 고르면 ABC처럼 반대 모드로 라우팅하고(직접 선택 포함), 시스템이 고른 우회 소스 정리도 같은 규칙을 쓴다. 라우팅·정리 코드는 `InputMethodRoutingCoordinator.swift`로 분리했다.
   - **해제 뒤에도 우회 소스가 남아 있으면 되돌린다.** 2026-10-07 18:17: 잠긴 동안 돌린 검사가 ABC를 "원래 소스"로 되돌려 놓아 해제 뒤에도 ABC였다. macOS가 되돌려 주지 않으면 알림이 없어 정리가 돌지 않는다. 그래서 기준선을 새로 잡을 때(앱 활성화·창·포커스 변경) 라우팅이 켜져 있고 시스템이 고른 우회 소스가 그대로면, 떠났던 KeyHue 모드(모르면 영문)로 같은 순서(반대 모드 → 그 모드)로 고른다.
   - **우회 소스는 회색이다.** 막대·HUD·메뉴 막대 아이콘·설정 창 색 목록에서 연동 중에는 ABC와 시스템 두벌식을 회색(`#8E8E93`)으로 보인다(`InputMethodIntegration.displaySettings`, 저장하지 않는 사본). 2026-10-07 표시 기록에서 ABC와 KeyHue 영문이 같은 파란색(`#0A84FF`)이라 "영문 → 영문", "안 바뀜"으로 보였다. 사용자가 정한 색이 있으면 그 색을 쓴다. 연동하지 않는 사용자의 ABC는 그대로 파란색이다. 연동 상태는 입력 소스 목록·설정이 바뀔 때만 다시 읽는다(색은 자주 읽힌다).
   - **실제 앱 검사는 잠긴 화면에서 시작하지 않는다.** 잠금 화면이 고른 ABC를 원래 소스로 기록해 해제 뒤 그대로 남겼다. 세 host runner는 입력 소스를 건드리기 전에 화면 잠금을 확인하고 멈춘다(`keyhue_require_unlocked_screen`, 종료 코드 75).
3. **의심스러운 순간과 표시를 로그에 남긴다.** 입력한 글자는 여전히 남기지 않는다.
   - `[Suspect] reason=rapid-toggles`: 3초 안에 전환이 세 번 이상(0.1초 안의 변경은 한 번, `SwitchBurstDetector`). 앱 ID와 변경 순서(`+0.000s Latin, +0.359s ABC, …`)를 함께 남긴다. 한 묶음에 한 번.
   - `[Suspect] reason=repair-while-typing`: 마지막 키 1초 안에 세션 복구가 단축키를 누름.
   - `display bar=[화면ID:#RRGGBB(:disconnected)(:hidden), …] hud=shown@화면ID|hidden`: 상태가 바뀔 때마다 막대가 어느 화면에 무슨 색으로 칠해졌는지, 그 화면이 연결돼 있는지, HUD가 어디 떴는지.
   - `input method routing: ABC the system selected pushed back …`: 2의 결과.

## 하지 않은 것

- 전환 단축키를 눌렀는데 소스가 안 바뀐 경우의 기록은 넣지 않았다. KeyHue의 키보드 감시가 ⌘Space 같은 시스템 단축키를 보는지 먼저 확인해야 한다.
- 사용자가 직접 표시하는 메뉴는 만들지 않았다. 문제가 생긴 순간 사람이 누르기를 기대하기 어렵다.

## 검증

- `InputMethodRoutingTests`: 잠금 화면에서 시작한 경우, 잠금 화면 ABC 뒤 돌아온 모드에서 반대 모드 → 원래 모드 순서로 한 번 고르기(두 방향), 로그인 창이 앞일 때 돌아온 알림은 기다렸다가 다음 알림에서, 입력 중이면 하지 않고 이후 라우팅이 대신함, 라우팅이 꺼져 있으면 아무것도 하지 않음. 기존 라우팅 테스트 유지.
- `InputMethodRoutingTests`(추가): 시스템 두벌식 라우팅(두 방향), 해제 뒤 남은 우회 소스를 떠났던 모드로·모르면 영문으로 되돌림, 입력 중이면 하지 않음. `detourSourcesAreGrayOnlyWhileIntegrated`, `DetourColorTests`(설정 창 색 목록, 저장 안 함).

- `SwitchBurstDetectorTests`: 17:41의 실제 순서를 한 번 보고, 라우팅 하나·몇 초 간격 전환은 보고하지 않음, 나중 묶음은 다시 보고.

- 잠금·해제 실제 확인(2026-10-07 18:17, 빌드 116): 해제 뒤 ⌘Space로 KeyHue 영문이 되자 정리가 돌았고(`… ok`) 다음 전환이 ABC 없이 한글로 갔다. 0.47초 뒤 ⌘를 누른 채 한 번 더 누른 전환은 세 번째 소스인 ABC로 가서 라우팅됐다(ABC가 켜져 있는 한 목록에서 뺄 수 없다). 해제 직후 ABC가 남아 있던 것은 잠긴 동안 돌린 검사 탓이었고, 위 보완(되돌림·runner 잠금 확인)을 넣었다. 보완의 실제 확인은 다음 잠금·해제에서 한다. 2026-10-09 사용자가 잠금·해제 뒤 동작을 실제로 확인했고 문제가 없었다.
