# 0067. 단어 고침은 한/영 양방향으로 하고, 터미널은 키로 지우고 다시 넣는다

- 상태: Accepted (수동 고침을 한/영 전환 대신 단축키로 하는 것은 [0068](0068-fix-words-with-a-shortcut.md)로 대체. 구현·단위 테스트·TextEdit 실제 검사 완료, Ghostty 터미널 고침 실제 검사는 권한 허용 후)
- 날짜: 2026-10-04
- 관련: [0064](0064-correction-modes-off-manual-automatic.md), [0065](0065-correct-all-apps-with-feedback.md), [0066](0066-ghostty-commit-after-tab-and-navigation-keys.md)

## 배경

사용자 보고: "한글로 바꿀 때"로 설정해 두었는데 `⌘Space`로 바꿔도 단어가 바뀌지 않는다. 한글뿐 아니라 영어도 같아야 한다. 옵션 이름도 이상하다.

입력기 서버 로그(단어 없이 결정과 이유만 남는다)로 확인한 원인은 셋이다.

1. **바꾼 곳이 Ghostty였다.** 터미널은 [ADR 0064](0064-correction-modes-off-manual-automatic.md)부터 기본 "고치지 않는 앱"이었다. 그래서 고침 경로에 들어가지 않았고, 로그도 안내도 없었다.
   - 터미널은 친 글자를 바로 프로그램(셸)에 보낸다.
   - 글자 위치도 알려 주지 않는다.
   - 따라서 입력기가 범위를 교체할 수 없다.
2. **반대 방향이 없었다.** ADR 0064는 첫 범위를 영문 → 한글로 정했다. 한글 모드로 친 영어 단어(`ㅗ디ㅣㅐ` → `hello`)는 고치지 않았다. Fork에서 한글 모드로 친 시도가 여기에 해당한다.
   - 판정기는 이미 두 방향을 판정한다(`MistypeVerdict.meantLatin`, ADR 0041의 경고가 쓰는 기준).
3. **이름과 설명이 맞지 않았다.**
   - "잘못된 모드로 친 단어 고치기 / 한글로 바꿀 때"는 한 방향만 말한다.
   - 설명의 "KeyHue가 확인한 앱에서만 동작"은 ADR 0065 이후 사실이 아니다.

## 결정

### 양방향 수동 고침
- 수동(기본)은 단어 직후 **반대 모드로** 바꾸면 고친다.
  - 영문 모드로 친 단어 + 한글로 전환 → 한글로 고친다(기존).
  - 한글 모드로 친 단어 + 영문으로 전환 → 친 키 그대로의 영어로 고친다. 판정기의 한글 모드 기준(ADR 0041, 사전 단어이면서 한국어 점수 −2.5 미만, 또는 음절이 되지 못한 모음)을 그대로 쓴다.
- 단어는 키로 기억한다. 화면의 글자는 영문이면 키 그대로, 한글이면 두벌식으로 조합한 글자다. 커서 확인은 조합된 글자 길이로 한다.
- 같은 모드로의 신호나 다른 입력 소스로의 전환은 고침 요청이 아니다. 후보를 버린다(`switchedAway`).
- 예외 단어와 되돌린 단어는 사용자가 본 글자로 비교한다. 같은 키(`rk`)도 영문 단어로 되돌린 것과 한글(`가`)로 되돌린 것은 서로 다르다.
- 자동은 계속 영문 → 한글만 Space에서 고친다. 한글 모드로 친 영어는 자동 설정에서도 전환할 때만 고친다. 자동의 반대 방향 기준은 오탐률을 따로 잰 뒤 정한다.

### 터미널
- 터미널(Terminal, iTerm2, Ghostty, Warp, kitty, Alacritty, WezTerm, `InputMethodCorrection.terminalApps`)도 고친다. 기본 제외 목록은 아래 "기본 제외 목록과 예외 단어"를 따른다.
- 터미널은 **수동으로만** 고친다. 자동 설정이어도 Space에서 명령어를 바꾸지 않는다(`CorrectionRouting`).
- 터미널은 위치를 알려 주지 않으므로 단어를 키로만 추적한다(`CorrectionPolicy`에 커서 nil).
  - 단어 시작: 활성화 직후, 또는 Space·Return 다음 글자.
  - 다른 키·Tab·방향키·클릭은 후보를 끊는다.
- 교체는 다음 순서로 한다(`KeyReplacement`):
  1. 원래 글자 수만큼 Backspace 키를 터미널 프로세스에만 보낸다(`postToPid`). 한글 음절과 낱자는 각각 한 글자다.
  2. 돌아온 Backspace는 입력기가 건드리지 않고 넘긴다(`PostedBackspaces`, 사용자의 되돌리기로 읽지 않는다).
  3. 마지막 Backspace를 터미널이 처리한 뒤 고친 글자를 넣는다.
- 키를 보내기 전 확인:
  - 같은 클라이언트가 맨 앞에 있다.
  - 조합 중인 글자가 없다.
  - 전환 단축키의 ⌘·⌃·⌥·Shift·fn이 모두 떼어졌다(⌘가 남으면 ⌘Backspace가 된다). 1초 안에 떼지 않으면 고치지 않는다.
- 바로 누른 Delete는 그 키를 소비하고, 같은 방식으로 고친 글자를 지우고 원래 글자를 넣는다.
- 터미널은 글자를 다시 읽을 수 없어 교체 전후 확인을 할 수 없다. 단어와 전환 사이에 다른 입력이 없었다는 정책의 조건만이 보증이다.
- 키를 보내려면 **입력기 프로세스의 손쉬운 사용 권한**이 필요하다.
  - 처음 필요할 때 입력기가 macOS에 한 번 요청한다(`CGRequestPostEventAccess`).
  - 권한이 없으면 고치지 않고 실패 이유 `keyPermission`(앱 ID와 이유만)을 유틸리티에 알린다. 유틸리티는 앱 탓이 아니라 허용할 곳을 안내한다. 제외 제안도 하지 않는다.
  - 설정의 "고치지 못한 앱" 목록의 [허용…]은 입력기에 권한 요청을 다시 시키고 손쉬운 사용 설정을 연다(`InputMethodCorrection.requestKeyPermission`, 내용 없는 알림).

### 기본 제외 목록과 예외 단어
- 기본 "고치지 않는 앱"은 **비어 있다.** ADR 0064는 식별자·명령어의 오탐 때문에 터미널과 코드 편집기 21개를 기본 제외했다. 그러나:
  - 기본인 수동은 사용자가 바꿔야만 고친다.
  - 잘못 고쳐도 바로 Delete로 되돌리고, 그 단어는 다시 고치지 않는다.
  - 사용자는 빈 목록에서 출발하리라 기대했다.
- 오탐은 앱이 아니라 **단어로** 막는다. 측정 도구가 고침 기준(판정기 기본값)의 오탐 전체를 `false-positives.txt`로 내고, 그것을 배포 예외 단어(`Resources/Mistype/reported-words.txt`)에 넣었다(측정: [data/0067-mistype-eval.md](data/0067-mistype-eval.md)).
  - 영문 모드 11개: `workdir`, `rhs` 등
  - 한글 모드 26개: `땐`, `꺼`, `샷`, `뜬` 등
  - 사용자가 본 글자로 쓴다. 영문 모드 단어는 친 영문, 한글 모드 단어는 조합된 한글이다.
  - 저장소 테스트에 일부러 넣은 오타 예시(`dkssud`, `rkskek`, `dkTek`, `dmdm`)는 뺐다.
  - 측정 도구는 이 목록을 영문은 영문 말뭉치, 한글은 한글 말뭉치로 읽어 기준을 바꿀 때마다 결과를 보인다.
- 자동 모드를 쓰다가 코드 식별자가 바뀌면 사용자가 코드 편집기를 목록에 추가한다. 설정 설명에 이 안내를 넣었다.
- 이미 목록을 저장한 사용자의 설정은 바꾸지 않는다. [기본값으로]를 누르면 빈 목록이 된다.

### 이름과 설명
- 옵션 이름은 "한/영을 잘못 친 단어 고치기"다.
- 선택지는 "끄기 / 한/영을 바꿀 때 / Space에서 자동으로"다.
- 설명에는 다음을 적는다:
  - 두 방향의 예
  - 자동은 영문 → 한글만 Space에서 고친다는 것
  - 터미널은 전환할 때만, 손쉬운 사용 권한으로 고친다는 것
- "확인한 앱에서만"은 지운다.
- 영어·한국어·일본어로 번역한다.

## 결과

- 사용자는 어느 방향으로 잘못 쳤든 평소의 한/영 전환으로 고칠 수 있다. 터미널(Claude Code 포함)에서도 같다.
- 터미널 고침은 다음 결과를 받아들인다:
  - 키를 보내는 동안 사용자가 친 키는 사이에 끼어들 수 있다.
  - 터미널이 Backspace를 한 글자 삭제로 처리하지 않는 프로그램(일부 전체 화면 앱의 특수 모드)에서는 결과가 다를 수 있다. 사용자는 바로 Delete로 되돌리고 그 앱을 제외할 수 있다.
- 입력기에 손쉬운 사용 권한이 하나 늘어난다. 권한은 터미널 고침에만 쓰며, 다른 앱은 지금처럼 범위 교체를 쓴다.
- Ghostty에서 고친 글자는 키 밖에서 넣으므로 붙여넣기 경로로 간다(ADR 0066과 같음).

## 검사

- 단위 테스트(먼저 작성해 실패 확인):
  - `CorrectionPolicyTests`: 반대 방향 수동 고침(Space까지, 치는 중), 조합 길이 커서, 한국어 유지, 같은 모드·외부 신호, 되돌리기, 보이는 글자 기준 예외·되돌린 단어, 자동은 반대 방향 없음, 위치 없는 클라이언트의 키 추적·단어 시작·양방향·도중 위치 소실
  - `DetectorCorrectionJudgeTests`: 한글 모드 영어 → 영어, 한국어 유지, 자동은 반대 방향 없음
  - `CorrectionRoutingTests`: 터미널은 자동 설정에서도 수동, 터미널만 키로 고침
  - `KeyReplacementTests`: 지울 글자 수와 넣을 글자, 되돌리기, 보낸 Backspace 인식, 다른 키, 도착하지 않은 키
  - `InputMethodCorrectionSettingsTests`: 기본 제외 앱 없음, 배포 예외 단어가 측정한 두 방향 오탐을 담고 일부러 넣은 오타 예시는 담지 않음
  - `CorrectionFeedbackStoreTests`: 권한 없음 안내
- 실제 앱 검사:
  - TextEdit 수동: 한글 모드 영어를 전환으로 고침, 바로 Delete로 복원, 영문 모드 유지, 치는 중인 단어, 한국어 단어 유지(`KEYHUE_TEST_TEXTEDIT_CORRECTION=manual`)
