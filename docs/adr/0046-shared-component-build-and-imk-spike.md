# 0046. 앱별 메타데이터로 빌드·검증·패키징을 공유하고, IMK 기술 검증 번들을 별도로 둔다

> 배포·버전·사용자 설치 흐름은 [ADR 0051](0051-single-app-distribution-and-managed-input-method.md)로 대체했다. 아래는 당시 결정이며 프로세스 경계·개인정보·단계별 검증 등 유지 범위는 0051을 따른다.

- 상태: Accepted (ADR 0002·0022의 스크립트 구성을 확장, 설치 부분은 ADR 0047, 한글 조합·입력 소스 아이콘은 ADR 0048로 갱신)
- 날짜: 2026-10-02

## 맥락
[ADR 0045](0045-experimental-input-method-component.md)는 입력기를 같은 저장소의 별도 앱으로 만들고 기술 검증부터 시작하기로 했다. 기존 스크립트는 `KeyHue.app`, 실행 파일, 버전 파일, 리소스와 ZIP 이름을 고정하고 있다. 특히 `package.sh`가 `build/dist` 전체를 삭제하므로 다른 구성 요소의 배포물이 사라진다.

사용자는 먼저 공통 스크립트와 IMK 기술 검증용 번들을 만드는 범위를 선택했다. 설치·입력 소스 등록·실제 클라이언트 호환성 검증은 빌드 성공과 구분해야 한다.

## 결정
- `scripts/components.sh`를 앱별 메타데이터와 서명 identity 선택의 공통 정의로 둔다. 입력은 열거된 `utility | input-method-spike`만 받으며 임의의 타깃·경로를 실행하지 않는다.
- `build-app.sh`, `check-bundle.sh`, `package.sh`, `notarize.sh`는 구성 요소 인자를 받는다. 인자 없는 기존 명령은 계속 유틸리티를 처리한다. 설치·UI 캡처·유틸리티 성능 측정은 역할별 스크립트로 유지한다.
- SwiftPM 빌드·앱 아이콘 생성·버전 주입·서명·ZIP/checksum은 공유한다. 번역·메뉴/HUD 아이콘·판정 모델은 유틸리티에, IMK 메타데이터·모드 이름·실험 안내는 기술 검증 번들에 포함한다.
- 버전은 유틸리티의 `VERSION`과 실험의 `Resources/InputMethodSpike/VERSION`으로 구분한다. 환경 변수 override도 각각 `VERSION`과 `SPIKE_VERSION`이다. 릴리즈 검증에 전달된 유틸리티 버전이 실험 버전을 덮어쓰지 않는다.
- 작업 디렉터리는 `build/work/<component>`로 나눈다. 패키징은 해당 구성 요소의 파일만 생성/교체하며 다른 ZIP·checksum·릴리즈 노트를 보존한다. 고정 최신 이름 `KeyHue.zip`은 유틸리티만 만든다.
- `check-bundle.sh`가 ID·실행 파일·버전·리소스·서명을 검사한다. universal 빌드에서는 arm64/x86_64도 확인한다. 입력기에는 백그라운드 속성·연결 이름·컨트롤러 클래스·두 모드 메타데이터를 추가로 확인한다.
- T단계 코드는 `Tools/InputMethodSpike/`의 별도 실험 타깃으로 둔다. 번들은 `KeyHueInputMethodSpike.app`, ID는 `io.github.sejoung.keyhue.inputmethod.spike`다. ADR 0045의 정식 입력기 타깃·ID로 간주하지 않는다.
- 실험은 두벌식 조합 표시/확정, Backspace, 두 영문 버퍼 정책의 비교를 제공한다. 고침·확정 단어 교체·고침 되돌리기는 아직 구현하지 않는다. 이 실험의 버퍼 정책을 정식 정책으로 확정하지 않는다.
- `verify.sh`는 기존 검사에 실험 코어 테스트·두 번들 검사·입력기 `--self-check`를 포함한다. self-check는 클래스/셀렉터·번들 메타데이터 검사이며 IMK 서버를 시작하거나 등록하지 않는다.
- `install.sh`는 유틸리티 전용으로 유지하고 입력기 인자를 거부한다. 입력기는 문서에 따른 테스트 계정의 명시적인 수동 등록 실험으로 시작한다. 현재 유틸리티 릴리즈 workflow·`vX.Y.Z`·최신 다운로드 링크에 실험물을 자동 게시하지 않는다.

## 결과
- 현재 유틸리티 명령과 다운로드 경로를 유지하면서 새 구성 요소가 공통 빌드 파이프라인을 쓸 수 있다.
- 실험용 코드·ID·버전을 정식 입력기와 구별하고, 공통 파이프라인의 회귀를 자동 테스트로 확인한다.
- 빌드/서명 성공만으로 등록·Gatekeeper·실제 IMK 콜백·앱 호환성이 검증됐다고 판단하지 않는다. 관찰 결과를 남기고 0단계 전에 버퍼·교체·모드 계약을 별도 ADR로 정한다.
- 설치·업데이트·제거 자동화는 IMK 수명 주기 실험 이후 설계한다. 유틸리티의 종료·복사·재실행 스크립트를 그대로 입력기에 적용하지 않는다.

## 검토한 대안
- **입력기용 빌드·서명·패키징 스크립트 전체 복제**: 버전 비교·서명 선택·번들 검사의 수정이 두 곳으로 갈라진다.
- **모든 스크립트를 단일 범용 앱 설치기로 통합**: 유틸리티와 IME의 등록·종료·업데이트 절차 차이를 숨기므로 채택하지 않는다.
- **정식 입력기 타깃부터 추가**: T단계의 임시 버퍼·메타데이터가 제품 계약으로 굳어질 수 있어 별도 실험 타깃을 둔다.
