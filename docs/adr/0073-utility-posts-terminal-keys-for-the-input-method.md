# 0073. 터미널 고침의 Backspace는 유틸리티가 보내고, 입력기는 권한을 갖지 않는다

상태: Accepted (구현·자동 검증·Ghostty 실제 검사 통과)

날짜: 2026-10-06

관련: [0051](0051-single-app-distribution-and-managed-input-method.md), [0062](0062-repair-input-method-session-with-previous-source-shortcut.md), [0067](0067-bidirectional-correction-and-terminals.md), [0068](0068-fix-words-with-a-shortcut.md)

## 배경

사용자 질문: 입력기가 따로 빌드되니 권한 허용도 두 번 해야 한다. 하나로 합치는 게 낫지 않나.

- **현재 권한:**
  - KeyHue: 입력 모니터링·손쉬운 사용
  - KeyHue 입력기: 손쉬운 사용. 터미널 고침에서 Backspace 키를 보낼 때만 쓴다(ADR 0067).
- **macOS 권한(TCC)은 번들마다 따로 저장된다.** 서명이 같아도 번들이 둘이면 허용도 둘이다.

번들 자체를 합치는 방안은 쓰지 않는다.

- 입력기는 `Input Methods`에 등록된 백그라운드 전용 번들(`LSBackgroundOnly`, `InputMethodConnectionName`)이어야 한다. 모든 앱의 입력이 이 프로세스를 거치고, 시스템이 필요할 때 실행·재실행한다.
- KeyHue를 꺼도 입력은 계속돼야 한다(ADR 0051).
- 메뉴 막대 앱과 한 프로세스가 되면, 앱이 손쉬운 사용 조회 등으로 멈출 때 모든 앱의 타이핑이 같이 멈춘다.

사용자가 받는 앱은 이미 `KeyHue.app` 하나다(ADR 0051). 빌드 대상이 둘인 것은 내부 구조다.

유틸리티는 이미 손쉬운 사용 권한이 있고, 세션 복구에서 키도 보낸다(ADR 0062). 그래서 키 보내기를 유틸리티로 옮기면 입력기의 권한이 필요 없다.

## 결정

### 역할
- **입력기:** "이 프로세스에 Backspace N개"만 유틸리티에 요청한다(`TerminalKeyPost.Request`: 대상 PID, 개수). 글자·단어·앱 내용은 보내지 않는다. 지우고 나서 글자를 넣는 일은 지금처럼 입력기가 한다.
  - 돌아오는 Backspace 세기(`PostedBackspaces`)
  - 마지막 키 뒤 고친 글자 넣기
  - 단어 상태·모드 선택
- **유틸리티:** 요청을 확인한 뒤 같은 키(키 코드 51, 수정키 없음, 표식 `TerminalKeyPost.postedKeyMarker`)를 그 프로세스에만 보낸다(`postToPid`). 확인 조건(`TerminalKeyPost.decide`)은 다음과 같다.
  - 대상 PID가 지금 앞 앱이다.
  - 보안 입력이 꺼져 있다.
  - 이벤트 전송 권한(손쉬운 사용)이 있다.
  - 개수가 1~256이다.

### 통로와 보낸 쪽 확인
- **통로:** `~/Library/Application Support/KeyHue/terminal-keys.sock`의 Unix 도메인 소켓이다. 폴더는 0700, 소켓은 0600이라 같은 사용자만 연결할 수 있다.
- **보낸 쪽 확인:** 같은 사용자의 다른 프로세스가 KeyHue 권한을 빌려 키를 보내지 못하게, 연결마다 상대 프로세스의 서명을 확인한다.
  - 소켓에서 상대의 audit token(`LOCAL_PEERTOKEN`)을 받는다.
  - 그 프로세스가 다음 서명 요건을 만족해야 한다: 입력기 번들 ID, 그리고 유틸리티 자신과 같은 인증서(`identifier "io.github.sejoung.keyhue.inputmethod.spike" and certificate leaf = H"…"`).
  - 확인되지 않으면 `untrusted`로 답하고 아무것도 보내지 않는다.
- **ad-hoc 서명:** 인증서가 없는 ad-hoc 빌드는 요건을 만들 수 없어 서버를 열지 않는다. 릴리즈와 `scripts/signing.sh create` 빌드는 인증서가 있다.
- 요청·응답은 JSON 한 줄이고, 연결마다 0.5초 시간 제한을 둔다. distributed notification은 보낸 쪽을 확인할 수 없어 쓰지 않는다.

### 유틸리티가 없을 때와 권한
- **유틸리티 응답이 없을 때**(KeyHue가 실행 중이 아님): 입력기에 이미 이벤트 전송 권한이 있으면 전처럼 직접 보낸다. 0073 이전에 허용한 사용자를 위한 것이다. 없으면 고치지 않는다(`keyPermission`). 입력기는 더 이상 macOS에 권한을 요청하지 않는다.
- **`keyPermission`의 뜻:** "KeyHue에 손쉬운 사용 권한이 필요함"으로 바뀐다. 안내와 설정의 [허용…]은 유틸리티 자신의 권한을 요청하고 손쉬운 사용 설정을 연다. 입력기에 권한 요청을 보내던 알림(`requestKeyPermission`)은 없앤다.
- **키보드 감시:** 유틸리티가 보낸 Backspace는 프로세스로 바로 가므로 키보드 감시를 거치지 않는다. 같은 표식이 붙어 있으면 키보드 감시도 사용자 입력으로 보지 않는다.

## 결과

- 새로 설치하는 사용자는 손쉬운 사용 권한을 KeyHue에만 주면 된다. 입력기 권한은 필요 없다.
- 터미널 고침은 KeyHue가 실행 중이어야 한다. 단, 입력기에 이미 권한을 준 사용자는 예외다. 일반 앱 고침과 입력은 KeyHue 없이도 된다.
- 키를 보내기까지 프로세스 왕복이 하나 늘어난다(같은 Mac, 수 ms).
- 소켓 파일 하나와 서명 확인 코드가 늘어난다. ad-hoc 빌드에서는 터미널 고침에 입력기 권한이 여전히 필요하다.

## 검증과 한계

- `TerminalKeyPostTests`: 요청·응답 형식, 잘못된 요청 거부, 확인 조건(앞 앱·보안 입력·권한·개수), 서명 요건 문자열, 소켓 경로 길이 제한.
- 서명 확인과 소켓 통신은 실제 프로세스 사이에서만 확인할 수 있다. Ghostty 고침 검사(`KEYHUE_TEST_GHOSTTY_CORRECTION=1`)는 원래 유틸리티를 끄고 돌았다. 0073부터는 유틸리티를 실행한 채 돌고, 모든 지우기가 유틸리티를 거쳤는지(입력기 로그 `via=utility`, `via=self` 없음)도 확인한다.
- 2026-10-06 실제 검사(macOS 26.6.2, Ghostty 1.3.1, KeyHue 0.2.5·빌드 97, 개발 인증서 서명):
  - **첫 실행(`.artifacts/input-method-ghostty/20261006-115924/`):** 지우기 16번 모두 유틸리티가 보냈다. 그러나 두 사례에서 Backspace가 하나 모자랐다(legacy `dkssud!` 7개 중 6개, kitty `가2` 2개 중 1개).
    - 입력기는 모두 받아 넘겼는데, 터미널이 하나를 셸에 보내지 않았다.
    - 이 구현은 처음에 모드 선택(`selectMode`)을 키를 요청한 뒤에 했다. 터미널이 Backspace를 처리하는 사이 입력 소스가 바뀐 것이 원인으로 보인다.
    - 0073 이전처럼 모드를 먼저 고르고 키를 요청하게 고쳤다. 요청이 실패하면 원래 모드로 되돌린다.
  - **고친 뒤(`20261006-130404/`):** legacy·kitty 48개 모두 통과, 지우기 16번 모두 `via=utility`.
  - **보낸 쪽 확인:** 서명이 다른 프로세스(python)가 소켓에 요청하자 `untrusted`로 거부했다. 키는 보내지 않았다.
- 이 Mac의 입력기에는 0073 이전에 준 손쉬운 사용 권한이 남아 있다. 검사에서는 모든 지우기가 유틸리티를 거쳐 그 권한을 쓰지 않았다. 권한을 뺀 상태의 검사는 하지 않았다.
- 이미 입력기에 준 손쉬운 사용 권한은 남는다. 필요하면 시스템 설정에서 직접 뺀다.
