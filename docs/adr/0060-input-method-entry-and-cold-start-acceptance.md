# 0060. 입력기 진입 준비는 실제 첫 키와 새 서버 프로세스로 검증한다

상태: Accepted (검사 계약, 프로그램 전환의 콜드 진입 실패는 미해결)

날짜: 2026-10-04 (실제 검사: 2026-10-03)

## 배경

[ADR 0059](0059-finalize-composition-on-input-source-change.md)는 입력기에서 떠날 때 남은 조합을 보존했다. 입력기로 들어올 때는 선택된 source ID가 한글이어도 키가 원시 영문으로 입력되는 실행이 남았다. 기동한 서비스의 재실행 통과만으로 콜드 스타트나 첫 키 준비를 완료로 표시할 수 없다.

[Squirrel의 진입 방향 보고](https://github.com/rime/squirrel/issues/1162)도 외부 TIS 선택과 실제 메뉴의 차이를 기록하며, 활성화 누락을 직접 관찰한 것은 아니라는 한계를 명시한다. KeyHue의 원인을 이 보고만으로 확정하지 않는다. [Apple IMKInputController 계약](https://developer.apple.com/documentation/inputmethodkit/imkinputcontroller)에 따라 연결된 실제 세션의 callback과 테스트 문서 결과를 확인한다.

## 결정

- 별도 opt-in `KEYHUE_TEST_TEXTEDIT_ENTRY_ONLY=1`로 같은 일반 텍스트 문서에서 세 번 검사한다. 한글 선택 뒤 첫 `d`가 `ㅇ`, 다음 `ks`가 `안`, 영문/ABC 전환 뒤 `a + Space`가 `안a `인지 확인한다. 첫 키 실패는 원시 `d`와의 일치 여부만 추가 기록하고 뒤 사례를 중단한다. 선택 재시도나 문서 재포커스로 실패를 복구한 뒤 통과로 집계하지 않는다.
- `KEYHUE_TEST_TEXTEDIT_COLD_START=1`은 매 회 ABC를 실제 메뉴로 선택한 임시 문서에서 자기 설치 경로·bundle ID와 일치하는 입력기만 정상 종료한다. 종료와 PID를 확인한 뒤 OS가 다시 시작한 서비스의 첫 키를 검사한다. 종료를 거부하거나 다른 경로의 서비스가 있으면 실패하며 강제 종료하지 않는다. 입력 소스 등록·목록·단축키 설정은 편집하지 않는다.
- 메뉴·짧은 worker·계속 실행되는 AppKit 앱·설정된 단축키를 구분한다. `MODE_SWITCH=app`은 전용 비활성 AppKit 앱 하나가 메인 run loop에서 아홉 소스 요청을 처리한다. 실행마다 새 앱을 띄워 입력 context가 갱신되는 효과를 반복 전환의 증거로 사용하지 않는다. 알림 요청과 결과 파일에는 소스·순번·PID·상태만 있고 입력 텍스트는 없다. 원래 환경을 복원하기 전에 자기 테스트 앱도 종료한다.
- `MODE_SWITCH=shortcut`은 사용자의 활성화된 이전 입력 소스 단축키(시스템 항목 60)를 읽고 수식 키의 누르기·떼기까지 HID 경로로 보낸다. 초기 메뉴 선택으로 한글/ABC의 이전 소스 쌍을 명시적으로 준비한다. 목표 소스와 전면 임시 창을 확인한 뒤 첫 문자를 보낸다. 현재 환경의 `⌘Space` 검사이며 Caps Lock·Fn·다른 전환 키의 통과로 확대하지 않는다.
- 콜드 검사에도 메뉴 준비가 있지만 준비 후 기존 서비스의 종료를 확인한다. 따라서 새 서버 프로세스 진입에 대한 검사이며, 재로그인·새 계정·최초 설치·TSM 전체 상태 초기화와 동일하지 않다. 전환 뒤 100ms 대기와 키별 helper 실행이 있는 검사다. 지연 없는 첫 키나 제품 성능 기준은 별도 대상이다.
- 제품의 TIS 선택 성공 반환값을 문서 context 준비 완료로 해석하지 않는다. callback 없는 컨트롤러를 임의 활성화하거나 키를 보관·재전송하는 보완은 추가하지 않는다. 일반 앱 고침 제한도 유지한다.

## 결과

macOS 26.6.2 (25G83), arm64, TextEdit 1.20, Swift 6.4 / macOS 27 SDK, 서비스 0.2.5·빌드 74에서 검사했다. 자료는 `.artifacts/input-method-textedit/20261003-<시각>/`다.

| 경로 | 실제 첫 키·조합 결과 | 근거 |
|---|---|---|
| 입력 메뉴, 매 회 새 입력기 프로세스 | 세 번 통과, 새 서버 PID·초기화·TextEdit 전달 확인 | `231557` |
| 설정된 `⌘Space`, 매 회 새 입력기 프로세스 | 한글/ABC 왕복 세 번 통과, 첫 키·조합·영문/공백 보존 | `232019` |
| 동일한 AppKit 선택 앱, 기동한 입력기 | 세 번 통과, 동일 sender PID의 연속 아홉 요청 | `233305` |
| 짧은 worker, 기동한 입력기 | 세 번 통과한 실행이 있으나 앞선 준비 검사 실패도 있음 | `233629`, `230445` |
| 짧은 worker, 새 입력기 프로세스 | 첫 키가 원시 `d`, 실패. 선택 ID는 한글 | `233800` |
| 동일한 AppKit 선택 앱, 새 입력기 프로세스 | 첫 키가 원시 `d`, 실패. 선택 요청은 성공 | `234817` |

단축키의 첫 시도 `231757`은 Space에 수식 flags만 주어 목표 소스로 전환되지 않았다. 수식 키 전이를 보내도록 테스트 전송을 수정한 뒤 `232019`에서 실제 source ID와 문자열을 확인했다. 초기 실패를 입력기 조합 실패로 분류하지 않는다. 매 선택마다 새 앱을 띄웠던 `232706` 통과는 동일 앱의 반복 전환 근거에서 제외하고 `233305`로 대체했다.

CLI 선택 helper의 AppKit 초기화와 2초 대기를 시험했지만 첫 조합 실패가 남았다(`230930`, `231123`). 실제 KeyHue worker에 창 없는 `NSApplication.finishLaunching()`을 추가한 프로토타입도 같은 빌드 74의 콜드 첫 키에서 원시 `d`로 실패했다(`234338`). 이 제품 변경은 제거했다. 최종 설치본은 기존 제품 코드로 복원했고 `.artifacts/input-method-e2e/20261003-234635/`의 기본 입력·고침/되돌리기·경합·필드/외부 선택 취소·업데이트/반복 설치는 통과했다. 스크립트 115개·ShellCheck와 helper의 Swift 6 실제 컴파일도 통과했다.

서비스를 백그라운드에서 먼저 기동하고 PID·`isFinishedLaunching`을 확인한 뒤 같은 AppKit 앱에서 선택하는 비교 `235647`도 첫 키가 원시 `d`로 입력됐다. 서버 기동 확인은 편집 클라이언트의 입력 context 준비 확인이 아니다. 이 테스트용 선행 기동 경로도 최종 runner에서 제외했다.

입력 메뉴·검사한 단축키·기동한 입력기에서의 AppKit 앱 결과를 프로그램 전환 전체나 실제 KeyHue 유틸리티의 자동 연동 전체로 확대하지 않는다. 프로그램 전환의 콜드 진입은 미해결이며, 유틸리티 자동 연동·다른 전환 키·빠른 첫 키·다른 앱/OS/CPU·범위 교체 능력과 제품 고침 옵션은 남아 있다. 상세 결과와 후속 조건은 [호환성 기록](../INPUT_METHOD_COMPATIBILITY.md)을 따른다.
