# 0070. 입력기 세션 확인은 아직 열려 있는 세션만 보내고, 복구는 타이핑 뒤로 미루며 실패한 앱도 다시 시도한다

상태: Accepted (Core·서버·유틸리티 구현, 단위 테스트 통과. 설치본의 Ghostty 라우팅 실제 확인 남음)

날짜: 2026-10-06

관련: [0061](0061-external-selection-does-not-open-input-method-session.md), [0062](0062-repair-input-method-session-with-previous-source-shortcut.md)

## 배경

사용자 보고: 한/영 전환이 가끔 안 된다. 메뉴 막대의 입력기는 바뀌었는데 포커스된 창에서는 바뀌지 않는다. 다른 앱을 갔다가 돌아오면 한글이 제대로 입력된다.

macOS 26.6.2 (25G83), KeyHue 0.2.5·빌드 95, Ghostty, `routeInputMethodPair` 켜짐 상태의 `~/Library/Logs/KeyHue/KeyHue.log`와 `KeyHueInputMethod.log`를 시각순으로 맞췄다.

| 시각 (2026-10-06) | 일어난 일 |
|---|---|
| 09:39:47.748 | 사용자 전환 → ABC (클라이언트 프로세스 안에서 처리) |
| 09:39:47.757 | 라우팅이 KeyHue 한글을 외부 TIS 선택 → 메뉴 막대는 한글 |
| 09:39:47.758 | 서버: Ghostty 세션 `activate mode=hangul`, mode callback → **확인 즉시 전송** |
| 09:39:47.759 | 서버: 같은 세션 `deactivate` |
| ~9초 | 서버에 키가 오지 않음(`editor input reached server` 없음) |
| 09:39:56 → 09:39:57.734 | Chrome에 갔다가 Ghostty로 돌아옴 → 세션 `activate hangul` |
| 09:39:58.101 | 키가 서버에 도달, 한글 입력 |

라우팅으로 전환할 때마다 Ghostty에서는 활성화 직후 1ms 안에 같은 세션이 닫혔다. 클라이언트 bundle ID가 기록된 빌드 95 이후 로그에서 라우팅 전환 6건 모두 그랬다. 영문 전환은 원시 ASCII와 결과가 같아 드러나지 않고, 한글 전환에서만 증상으로 보였다.

ADR 0062의 2026-10-05 보완은 선택 변경 알림 경로의 거짓 확인만 미뤘고 activate·mode callback의 확인은 그대로 즉시 보냈다. 유틸리티는 위 확인으로 `.acknowledged`를 받아 복구 단축키를 누르지 않았다. `.acknowledged`는 로그에 남지 않아 겉으로는 아무 일도 없었다.

클라이언트가 왜 바로 세션을 닫는지는 확인하지 못했다(HIToolbox 내부). 순서로 보면 클라이언트 안에서 처리한 ABC 선택이 외부 선택을 다시 덮는 것으로 추정한다. 다른 앱으로 일반화하지 않는다.

같은 로그에서 다른 두 문제도 확인했다.

- **오래된 서버의 침묵:** 09:37 앱은 빌드 95로 바뀌었고 설치된 서버는 확인 알림이 없는 예전 빌드(pid 649, `needsUpdate=true`)였다. Ghostty와 Chrome이 모두 `unrepaired`로 끝났다.
- **영구 제외:** `unrepaired`가 된 앱(PID)은 KeyHue가 다시 실행될 때까지 복구 대상에서 빠졌다. 한 번의 잘못된 판정이 그 앱의 복구를 계속 끈다.
- **타이핑 취소:** 확인을 기다리는 250ms 안에 키나 클릭이 있으면 복구를 취소하고 다시 시도하지 않았다. 전환하자마자 치는 사용자는 복구를 받지 못한다.

## 결정

- **서버 확인은 열린 세션만:** activate·mode callback·선택 변경의 확인을 모두 `SessionAcknowledgement.confirmationDelay`(80ms, 이전 이름 `selectionChangeDelay`) 뒤에 보낸다. 그때 세션이 아직 활성일 때만 보낸다(`forModeCallback(requestedID:sessionActive:)`). 선택 변경은 기존대로 앞 앱 조건도 본다. callback은 앞 앱 조건을 더하지 않는다. 클라이언트 bundle ID와 앞 앱이 다른 앱에서 거짓 실패가 생기지 않게 하기 위해서다. 확인의 내용(모드 ID만)은 바뀌지 않는다.
- **타이핑 중에는 미루기:** 기다리는 동안 사용자의 키·클릭이 있으면 취소하지 않고 기다림을 그 시점부터 다시 시작한다. 키 사이에는 누르지 않고, 입력이 250ms 멈춘 뒤에야 단축키를 누른다. 그동안 확인이 오면 아무것도 누르지 않는다. 앞 앱이 바뀌면 이전처럼 생략한다. 복구 중의 상호작용 처리는 0062 그대로다.
- **제외는 기한까지만:** 두 번 누른 뒤에도 확인이 없는 앱의 제외는 `unrepairedRetryInterval`(10분) 동안만 유지한다. 그 앱이 앞 앱일 때 확인이 오면 바로 해제한다. 입력기를 설치·업데이트하면 모든 제외를 지운다(`forgetUnrepairedApps`).
- **오래된 서버에서는 판정하지 않기:** 설치된 입력기가 앱에 들어 있는 것과 다르면(`InputMethodInstallationStatus.needsUpdate`) 복구를 생략하고 사유를 로그에 남긴다. 확인을 보내지 못하는 서버의 침묵을 실패로 세지 않는다.

## 결과

- 이번 경우는 확인이 오지 않으므로 유틸리티가 이전 입력 소스 단축키를 두 번 누른다. 클라이언트 안에서 목표 모드를 선택하게 한다(0062). 단축키가 꺼져 있거나 Caps Lock만 쓰면 0061의 제약이 그대로 남는다.
- 확인이 80ms 늦어진다. 유틸리티 기한(250ms)의 절반 안이라 정상 세션은 여전히 확인된다. 서버가 새로 실행되는 시간이 기한보다 길면 필요 없는 복구가 일어날 수 있지만 최종 소스는 같다(0062와 같음).
- 타이핑이 멈춘 뒤 누르므로, 그 전에 입력된 글자는 원시 ASCII로 남는다. 누르는 50ms 사이에 다시 친 키는 중간 소스로 들어갈 수 있다(0062와 같은 위험).
- 텍스트 입력 문맥이 없는 앱에서는 10분에 한 번까지 단축키 왕복이 보일 수 있다.
- 같은 버전의 개발 빌드처럼 설치본과 내용이 다르면 업데이트 전까지 복구를 하지 않는다.

## 검증과 한계

`InputMethodSessionRepairTests`가 가짜 시간으로 검사한다: 키 사이에는 누르지 않고 멈춘 뒤 누름, 타이핑 중 확인이면 누르지 않음, 대기 없는 상호작용 무시, 타이핑 중 앞 앱 변경 생략, 기한 뒤 재시도, 앞 앱 확인으로 제외 해제, 설치 후 제외 초기화, 다시 제외된 앱이 이전 기한에 풀리지 않음. `SessionAcknowledgementTests`는 닫힌 세션의 callback이 확인이 아님과 지연이 기한 안에 있음을 검사한다. 업데이트 판단의 실제 연결은 단위 테스트로 검사하지 않는다.

설치본에서 Ghostty 라우팅(ABC → KeyHue 한글)이 `repaired`로 끝나고 첫 키가 한글로 입력되는지는 아직 확인하지 않았다. 확인할 때는 `KeyHue.log`의 `input method session repair:` 줄과 서버 로그의 `activate`·`deactivate`·`editor input reached server` 순서를 본다.
