# 0031. 앱 전환 뒤 대기를 40 ms로 줄이고, 덮어쓰기는 알림을 받는 즉시 바로잡는다

- 상태: Accepted
- 날짜: 2026-09-29

## 맥락
"HUD를 꺼도 앱 전환 때 입력 소스가 바로 바뀌지 않고 약간 늦다"는 보고가 있었다.

ESC나 직접 한/영 전환은 약 25 ms에 반영되는데, 앱 전환은 **일부러 0.1초 기다린 뒤** 바꿨다(ADR 0007). 앱이 활성화된 직후 시스템(TSM)이 새 앱에 이전 입력 소스를 다시 적용하므로, 그보다 먼저 바꾸면 덮어써지기 때문이다. 0.1초는 실측 없이 넉넉하게 잡은 값이었다. 그 밖에도 다음 두 가지가 전환을 늦출 수 있었다.
- 새 앱에 붙는 AX 작업과 창 목록 조회가 전환 예약보다 먼저 실행됐다.
- 덮어써진 경우에는 0.25초 뒤에야 확인하고 다시 바꿨다.

측정용 앱 두 개를 번갈아 활성화하며 쟀다(`Tests/perf/app-switch-latency.sh`).

**시스템 덮어쓰기** (KeyHue 없이, 활성화 알림 뒤 N ms에 ABC로 전환)

| 활성화 후 전환까지 | 덮어써짐 |
|---|---|
| 0 ms | 9/20 |
| 10 ms | 2/20 |
| 20 ms 이상 | 0/88 |

덮어쓰기 알림은 활성화 후 12–36 ms에 왔다.

**수정 전 KeyHue** ("앱을 바꿀 때 › ABC로 전환", 활성화 알림부터 ABC까지): 중앙값 129 ms, 최대 158 ms (20회).

## 결정
- **대기 시간 `appSwitchSettleDelay`를 0.1초에서 0.04초로 줄인다.** 덮어쓰기가 사라지는 20 ms의 두 배다. 같은 값을 쓰는 창 전환도 함께 빨라진다.
- **덮어쓰기는 알림으로 바로잡는다.**
  - 자동 전환 뒤 0.25초 동안 결과를 지켜본다.
  - 그 사이 입력 소스 알림이 목표와 다른 값을 알려 오면, 다음 런루프 차례에 한 번만 다시 바꾼다. 알림 처리 중에 바로 바꾸면 관찰자 안에서 같은 흐름이 다시 불리므로 한 차례 미룬다.
  - 되돌려진 입력 소스는 앱·창 기억에 기록하지 않는다.
  - 0.25초 끝의 확인은 알림을 놓쳤을 때를 위한 대비로 남긴다.
- **앱 전환은 전환 시점에 판단한다.**
  - 대기가 끝나는 순간의 실제 입력 소스와 새 앱의 앞 창으로 무엇을 할지 정한다.
  - 호출자(AppDelegate)는 전환을 예약한 **뒤에** 새 앱에 붙기(AX)와 활성 화면 찾기를 한다. 그래서 예약 시간이 그 작업만큼 밀리지 않고, 판단 시점에는 앞 창을 이미 알고 있다.

## 결과
- **수정 후 KeyHue**: 110회 중 109회 성공, 깜빡임 0.
  - 중앙값은 66–73 ms (측정 묶음마다), 최대 147 ms였다. 이 147 ms를 뺀 나머지는 모두 94 ms 이하였다.
  - 실패 1회는 설치 직후 첫 측정에서 나왔다. 실패 기록 출력을 넣기 전이라 원인은 확인하지 못했고, 이후 KeyHue 재시작 직후를 포함한 90회에서는 다시 나오지 않았다.
  - 수정 전 기준값(중앙값 129 ms)은 20회만 쟀다.
- 단위 테스트
  - 대기 시간이 실측으로 안전한 범위(20–50 ms) 안인지
  - 덮어쓰기 알림을 받으면 바로 한 번 다시 바꾸고, 마지막 확인은 중복 실행하지 않음
  - 되돌려진 값은 기억하지 않음
  - 지켜보는 시간이 지난 뒤의 변경은 사용자의 선택으로 두고 되돌리지 않음
  - 앞 창은 전환 시점에 읽음
  - 전환 시점에 이미 목표면 아무것도 하지 않음
- 로컬 성능: `Tests/perf/app-switch-latency.sh`
  - 실패나 깜빡임이 있거나 중앙값이 100 ms를 넘으면 실패한다.
  - `race` 모드는 KeyHue 없이 시스템 덮어쓰기를 재현한다.
- 한계
  - 측정용 앱은 가볍다. Chrome·Electron처럼 무거운 앱에서는 시스템의 재적용이 더 늦을 수 있지만, 그 경우도 알림으로 바로 다시 바꾼다.
  - 자동 전환 직후 0.25초 안에 사용자가 직접 입력 소스를 바꾸면 되돌린다. 기존(0.25초 뒤 확인)과 같은 범위인데, 이제는 되돌리는 시점이 더 빠르다.
