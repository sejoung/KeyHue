# 입력기 실제 앱 호환성 기록

순수 로직 테스트와 실제 앱 검증을 구분한다. 전체 자동 검증이 통과해도 아래 앱 호환성은 별도로 확인한다. 실험 계약은 [ADR 0056](adr/0056-isolated-correction-and-undo-probe.md), [ADR 0057](adr/0057-automatic-correction-observation-and-input-priority.md), [ADR 0058](adr/0058-external-mode-callbacks-and-native-editor-acceptance.md), [ADR 0059](adr/0059-finalize-composition-on-input-source-change.md), 실행 절차는 [TESTING](TESTING.md#실험-입력기-연동-검증)을 따른다.

### 확인한 문제와 수정

기존 host 검사는 `handleEvent`가 거부하면 `keyDown`도 호출해 같은 이벤트가 다시 IMK에 전달될 수 있었다. 이전 `.artifacts/input-method-e2e/20261003-110817/`의 통과 기록은 이 제약을 가진 초기 증거다. 한 번 전달하도록 바꾼 `.artifacts/input-method-e2e/20261003-114448/`에서는 KeyHue 한글의 첫 Space가 빠졌다. 남은 조합과 공백을 하나의 `insertText`로 확정하고 Space를 소비하도록 수정했으며, 이후 기본 검사와 순수 회귀 테스트가 통과했다.

초기 고침 실행 `114949`·`115752`에서는 원문과 영문 모드로 남아 실패했다. `120559` 진단 실행에서 6타 추적과 Space 전달이 정상임을 확인했다. `uniqueClientIdentifierString()`을 안정된 클라이언트 ID로 사용해 첫 관찰 때 다르다고 판정하고 있었고, 확정 뒤 IMK가 반환하는 `{NSNotFound, NSNotFound}`를 활성 조합으로 해석하고 있었다. 세션 UUID와 유지 중인 클라이언트 객체로 소유권을 비교하고, 같은 클라이언트가 유효한 조합 범위를 보고한 이력이 있는 격리 실험에서만 비활성 범위를 해석하도록 수정했다. 원문·빈 선택·모드·UTF-16 범위 확인은 유지한다. `120941`에서 전체 acceptance가 통과했다. 상세 계약은 [ADR 0056](adr/0056-isolated-correction-and-undo-probe.md)을 따른다.

초기 ABC 선택 실패·포커스 상실·잠금 화면 중단도 있었다. 활성 창이 없거나 검사 중 포커스를 잃으면 키를 보내지 않고 실패로 종료한다. 실패 실행도 원래 입력 소스를 복원한다. 유틸리티 자동 연결의 간섭을 피하려고 runner가 유틸리티를 잠시 종료하지만, 초기 선택 실패 원인 전체를 이것으로 단정하지 않는다.

자동 관찰 도입 후 조회 중 자연 Backspace가 재진입하면서 이전 관찰과 새 되돌리기가 경합했다. 조회 전후·효과 직전 세대 검사와 중단 처리를 보완했다. 반복 burst 검사는 남은 marked text를 취소하는 테스트 초기화에서 정체돼, 정상 Space로 확정한 뒤 새 문서를 시작하도록 고쳤다. 초기 타임아웃의 actor 문맥 오류도 수정했고 별도 60초 watchdog과 단계별 로그를 추가했다. 이 정체를 입력기 RPC 교착으로 단정하지 않는다. 수정한 `134316` 실행에서 모든 사례가 통과했다.

TextEdit 한글 입력이 서버 callback에 도착하는 것도 로그에서 확인했다. 영문 결과 보존·Latin source ID 확인을 영문 한 글자 marked text나 모든 영문 키의 IMK callback 확인과 동일시하지 않는다. 문서 왕복 때 마지막 글자가 보이는 것만으로 조합 종료를 보장하지 않는다. 이 검사는 자동 완성·영문 밑줄·모든 기호/단축키·교체 능력의 완료 증거가 아니다. TextEdit 고침은 전용 앱 제한 때문에 실행되지 않는다.

위 빌드 73에서는 외부 worker 선택과 실제 메뉴 선택의 결과 차이가 미해결이었다. 아래 빌드 74의 후속 검사로 확인된 이탈 시 조합 유실을 수정했다. TIS 선택 조회 성공만으로 활성 문서의 입력 context가 준비됐다고 판단할 수 없다. 유틸리티 자동 연동·시스템 전환 단축키의 실제 문서 경로를 추가 확인해야 한다. `commitComposition` sender fallback, 다른 이벤트 인터페이스, Latin script 메타데이터 변경을 시험했지만 worker 실패를 해결하지 못해 최종 코드에는 포함하지 않았다. 원인을 해당 항목으로 단정하지 않는다.

초기 `System Events key code` 실행의 문자열 통과는 실제 IMK 전달을 충분히 확인하지 못한 근거라 위 결과에 합치지 않았다. 실제 메뉴 전체 검사 `170845`는 일반 텍스트 11개·RTF 일부가 통과한 뒤 120초 watchdog으로 종료됐다. 이후 종류별 검사로 분리했고 두 종류 전체 runner의 한도는 300초로 조정했다. 준비 전 AX 창 조회·메뉴 번역 차이·포커스 상실도 실패로 기록했다. 업데이트 직후 첫 조합 누락과 이후 서버 기동을 관찰한 실행도 있어 콜드 스타트 준비 보장은 남아 있다.

## 2026-10-06 라우팅 전환의 거짓 확인 (ADR 0070)

macOS 26.6.2, KeyHue 0.2.5·빌드 95, Ghostty에서 라우팅(ABC → KeyHue 한글)으로 전환했다. Ghostty는 세션을 활성화하고 mode callback을 받은 1ms 뒤 같은 세션을 닫았다. 서버의 즉시 확인 때문에 유틸리티는 복구를 건너뛰었다. 메뉴 막대는 한글인데 키는 원시 ASCII로 입력됐고, 앱을 바꿨다 돌아오면 고쳐졌다. 확인은 이제 80ms 뒤 열린 세션에서만 보낸다. 기다리는 동안의 입력은 복구를 미루고, 실패한 앱은 10분 뒤 다시 시도하며, 업데이트 전 서버에서는 판정하지 않는다([ADR 0070](adr/0070-acknowledge-only-open-sessions-and-retry-repair.md)). 설치본의 실제 확인은 남아 있다.

같은 날 설치 뒤(빌드 96) 두 가지가 더 보였다. 하나는 ⌘Space가 ABC를 거쳐 전환마다 라우팅·세션 복구(0.5초)를 거친 것이다. 다른 하나는 그 사이 친 키를 입력기가 받지 못해 터미널 고침이 "고칠 단어 없음"이 된 것이다. 라우팅은 떠나는 모드를 먼저 선택해 ABC가 이전 소스로 남지 않게 했다. 터미널 고침은 수정키를 뗄 때까지 10초 기다린다. 화면 잠금 때 라우팅이 ABC 연결 옵션을 끄던 문제도 고쳤다([ADR 0071](adr/0071-route-through-the-leaving-mode-and-wait-for-modifier-release.md)). 빌드 97에서 메뉴로 맞추지 않은 ⌘Space 전환 검사 6개와 기존 입력·고침 검사 39개가 통과했다(`.artifacts/input-method-ghostty/20261006-105703/`, `110016/`).

### 실패와 수정 범위

- 업데이트 직후 최초 IMK 실행 `input-method-e2e/20261006-175401/`은 기본 4개 사례 뒤 Latin→Hangul 전환의 첫 글자 조합 표시에서 실패했다. 서버 로그에는 requested Hangul / observed Latin callback 뒤 모드 변경 알림이 조합을 확정한 기록이 있다. **동일한 실행 파일로 재실행하면 통과했지만 간헐적 전환 문제의 해결 근거로 쓰지 않는다.** 첫 키 검사에 대기나 재전송을 추가하지 않았다. 전후 입력 소스·configured IDs는 두 실행 모두 일치한다.
- 최종 번들 업데이트 후 `181728`·재실행 `182202`는 실제 테스트 창 포커스를 잃어 기본 입력 중 중단됐다. 포커스 조건을 완화하지 않고, 실패 진단에 활성/키 창 여부·앞 앱 ID를 추가했다. 최종 `182525`는 전체 acceptance와 원래 source ID·configured IDs 복원을 확인했다. 최종 재빌드로 실행 파일이 달라졌을 때의 사전 거부도 확인했으며, 이전 설치본의 통과를 새 번들의 통과로 간주하지 않았다.
- TextEdit 수동 고침은 `175551`·`175957`·진단 `180104`에서 첫 고침/되돌리기 뒤 문서 준비가 중단됐다. 진단은 `focusedFixture=true, mainFixture=true`인데 창 배열의 첫 항목이 달랐음을 확인했다. 준비 시 `AXMain`을 지정하고 클릭 전 `AXMainWindow`로 확인하도록 runner를 고쳤다. `180149`에서 수동 고침 전체가 통과했다.
- 기본 문서 검사 `180413`은 Return 사례 뒤 문서 준비의 불필요한 재클릭에서 포커스 확인으로 중단됐다. 이미 실제 포커스가 있는 문서는 그대로 준비하도록 보완한 `180710`에서 두 문서와 창 왕복이 통과했다. 다른 문서로 이동할 때의 실제 클릭, 키 직전 PID·`AXFocusedWindow` 확인, 포커스를 잃으면 중단하는 조건은 유지한다.
- TextEdit 각 실행의 전후 원래 입력 소스·configured IDs 복원을 runner가 확인했다. Ghostty는 후속 runner의 preflight와 시작 상태가 일치함을 별도로 비교했고 `restoration-next-preflight.json`으로 보존했다. 각 runner는 테스트 창만 닫고 원래 유틸리티 실행 상태를 복원했다.

## 다음 완료 조건

격리된 클라이언트의 후보 추적·교체·모드 전환·되돌리기·자동 확인·빠른 다음 입력과 외부 편집 취소 사례는 완료했다. 제품의 수동·자동 고침과 설정 연결은 ADR 0064~0068로 구현했으며, 다음 실제 환경 검사가 남아 있다.

1. 외부 선택이 입력기 세션을 만들지 않는 제약(ADR 0061)은 서버 확인이 없을 때 이전 입력 소스 단축키를 두 번 누르는 복구(ADR 0062)로 대응한다. TextEdit의 새 클라이언트·서버 재시작은 `MODE_SWITCH=repair`로 통과했다. 설치된 유틸리티의 자동 전환 경로와 다른 앱 확인이 남아 있다. Ghostty는 라우팅 전환 직후 세션을 닫는다. 이 경우의 거짓 확인은 ADR 0070에서 막았고 실제 확인이 남아 있다. 메뉴·설정된 `⌘Space`의 새 서버 진입과 외부 이탈 조합 보존은 확인했다. 다른 전환 키·알림 전 다음 키·빠른 포커스/모드 경합·실제 모드 거부 후 복구는 남아 있다.
2. 앱별 기본 입력과 클라이언트 능력 판별, RPC 지연·실패 계약과 성능 기준을 확인한다.
3. 판정기 임계값의 오탐·혼용 평가와 추가 앱의 입력·고침·보안 필드를 확인한다. 설정 전달과 앱 제외 정책은 구현되어 있으며, TextEdit·Ghostty의 확인 결과를 미검사 앱 전체의 호환성으로 확대하지 않는다.
